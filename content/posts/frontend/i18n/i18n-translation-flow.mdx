문구 한 줄을 바꾸려면 개발자와 번역자가 번갈아 움직여야 했습니다. 그 와중에 번역이 어긋나고, 영어가 ko/ja 자리로 흘러들어갔습니다.

한동안은 원래 번거로운 일이라고 생각했습니다. 그런데 곱씹어 보니 번거로움보다 큰 문제가 있었습니다. **한 값에 주인이 둘**이었습니다. `en`은 코드도 쓰고 시트에서도 편집됐고, 그래서 merge할 때 어느 쪽 값이 남을지가 운에 달려 있었습니다.

이 글은 그 플로우를 컬럼마다 주인을 하나만 둔다는 원칙으로 다시 설계한 기록입니다. 화려한 기술은 없습니다. 누가 무엇의 주인인지 한 번 분명히 정하고, 나머지는 스크립트와 CI에 맡겼습니다. (next-intl, en/ko/ja 3개 로케일)

---

## 1. 손이 많이 갔고, 영어가 새어 나왔다

i18n 자체는 이미 붙어 있었습니다. next-intl로 `t()`를 부르면 화면에 다국어가 나오긴 했습니다. 그런데 딱 거기까지였습니다.

문구 하나를 넣으려면 개발자가 `en.json`, `ko.json`, `ja.json` 세 파일에 키를 직접 써넣고, 같은 내용을 `translations.tsv`에도 반영하고, TSV를 구글 스프레드시트로 push해야 했습니다. 그러면 번역자가 시트에서 ko/ja를 채우고, 이걸 다시 TSV로 내려받아 `en/ko/ja.json`으로 build했습니다. 문구 한 줄에 여러 파일을 오가야 했고, 번역이 어긋나거나 키가 안 맞는 일도 잦았습니다.

| 영역 | 처음 상태 |
| --- | --- |
| 신규 문구 반영 | `t()`로 감싸도 자동 반영되지 않음. 개발자가 `en/ko/ja.json`, `translations.tsv`를 직접 편집 |
| 소유권 경계 | `en`을 코드도 쓰고 시트에서도 편집. 주인이 둘 |
| 영어 역류 | merge/pull에서 영어가 ko/ja로 흘러들어감. 이를 되돌리는 응급 스크립트까지 존재 |
| 개발자 공수 | 문구 하나에 여러 파일. 과함 |

불편한 건 참으면 그만이지만, `en`의 주인이 둘이라는 건 성격이 다른 결함이었습니다. `ko/ja`는 번역자가 쓰는데, merge/pull 과정에서 영어가 슬그머니 흘러들어갔습니다. 실제로 레포에는 draft merge 뒤 영어로 돌아간 ko/ja 값을 되돌리는 응급 스크립트까지 있었습니다.

## 2. 충돌은 락이 아니라 소유권으로 푼다

충돌을 없애는 방법으로는 보통 락이나 머지 전략을 떠올립니다. 하지만 그건 충돌이 *난 뒤에* 수습하는 방식입니다. 저는 한 발 앞에서, **한 셀에 주인을 하나만** 두어 충돌이 애초에 생기지 않게 하고 싶었습니다.

| 컬럼 | 주인 | 흐름 |
| --- | --- | --- |
| key + en | 코드 (leaf = 영어 원문 = Figma 카피) | 코드에서 시트로 (단방향) |
| ko / ja | 번역자 (시트) | 시트에서 코드로 (단방향) |

나머지 규칙은 이 표에서 나옵니다.

- `en.json`은 코드에서 자동으로 생성됩니다. 사람이 손대지 않습니다.
- `ko.json`, `ja.json`에는 실제로 번역된 키만 담습니다. 미번역 키는 런타임에 영어로 폴백되므로 화면이 깨지지 않습니다.
- `pull`은 ko/ja만 가져옵니다. `en`은 시트에서 내려오지 않으니 영어가 ko/ja로 흘러들 경로가 없습니다. 앞서 본 응급 스크립트도 여기서 필요 없어집니다.

이 구조를 받치는 키 컨벤션은 **leaf 세그먼트를 곧 영어 원문으로** 두는 것입니다. `eval.dashboard.evaluation run metric`의 en 값은 `evaluation run metric`입니다. leaf가 영어이니 `en.json`은 코드에서 생성하면 되고, 번역자는 영어를 뺀 나머지 언어만 시트에서 관리하면 됩니다.

원칙은 이게 전부입니다. 나머지는 이걸 파이프라인으로 옮기는 일이었습니다.

## 3. 세 주인, 그리고 그 사이를 잇는 CI

이 플로우에 등장하는 주체는 셋입니다. 개발자, 번역자, 그리고 그 사이를 잇는 CI입니다. 개발자와 번역자는 자기 컬럼만 만지고, 그 사이를 옮기는 일은 CI와 스크립트가 맡습니다.

| 주체 | 무엇의 주인인가 | 하는 일 |
| --- | --- | --- |
| 개발자 | `key`, `en` (코드) | `t("...")` 쓰고 커밋 |
| 번역자 | `ko`, `ja` (시트) | 시트 채우고 "번역 완료" 버튼 |
| CI/스크립트 | 그 사이 전부 | 키 추출, 시트 동기화, PR 생성 |

```mermaid
flowchart TD
	Dev["개발자: t(...) 작성 + commit"] -->|"pre-commit (오프라인)"| EN["en.json (build-en 생성)"]
	Dev -->|"qa/main 머지"| CI1["CI: i18n-sync"]
	CI1 -->|push-keys| Inbox["i18n_dev_inbox (key + en)"]
	CI1 -->|promote| Trans["i18n_translations"]
	Tr["번역자: ko/ja 입력"] --> Trans
	Trans -->|"번역 완료 버튼"| Disp["repository_dispatch"]
	Disp --> CI2["CI: i18n-pull"]
	CI2 -->|"pull ko/ja"| PR["sync PR (ko/ja.json)"]
	EN --> Repo["repo = 배포 소스"]
	PR --> Repo
```

**커밋과 시트 push는 별개입니다.** 커밋은 로컬 `en.json`만 갱신하고(오프라인), 시트에 올리는 push/promote는 qa/main 머지 때 CI가 돌리고, pull은 "번역 완료" 버튼을 누르거나 수동으로 실행합니다. 빌드/배포는 항상 커밋된 JSON만 씁니다. 라이브 fetch가 없으니 같은 커밋이면 언제 빌드해도 번역 결과가 같습니다.

시트는 탭 두 개로 나눴습니다. 번역자의 작업 공간과 CI가 올리는 신규 키를 섞지 않기 위해서입니다.

- `i18n_dev_inbox`: 스크립트만 쓰는 탭입니다. `push-keys`가 코드의 키 중 아직 시트에 없는 것을 en과 함께 추가합니다. 번역자는 이 탭을 보지 않습니다.
- `i18n_translations`: 번역자의 작업 공간이자 ko/ja 원본입니다. `promote`가 신규 키만 여기로 append하고, `pull`은 여기서 ko/ja만 읽습니다.

헤더 1행은 `key`와 로케일 컬럼(`en` `ko` `ja`, 순서 무관)이고, 탭 이름은 환경변수 `GOOGLE_SHEETS_DEV_TAB` / `GOOGLE_SHEETS_TRANSLATIONS_TAB`로 지정합니다.

## 4. 개발자는 `t()` 쓰고 커밋하면 끝

`t("...")`를 쓰고, 저장하고, 커밋하면 끝입니다.

첫째, 화면 문구는 반드시 next-intl `t()`로 감쌉니다.

```typescript
const t = useTranslations("LlmEval.Dashboard.Chart");
<button>{t("Edit chart")}</button>   // key: LlmEval.Dashboard.Chart.Edit chart
```

둘째, `en.json`은 저장할 때 자동으로 채워집니다. `pnpm dev`를 켜면 `instrumentation.ts`가 dev 전용 watcher(`build-en --watch`)를 함께 띄워, `t("New copy")`를 저장하면 `en.json`에 바로 들어갑니다. `pnpm i18n:build-en`을 수동으로 실행해도 되고, 커밋할 때 pre-commit이 한 번 더 맞춰 줍니다.

셋째, 리치 텍스트(`t.rich`)나 leaf가 영어가 아닌 시맨틱 키는 호출 바로 위에 영어 원문을 `// i18n-en:` 주석으로 답니다. 일반 키는 leaf가 곧 영어라 주석이 필요 없습니다. 아래 예시의 `AddToWorkspaceRoleInfoBanner`는 영어가 아닌 짧은 시맨틱 ID이고, 영어 원문은 그 위 주석에 있습니다.

```typescript
// key "AddToWorkspaceRoleInfoBanner" 는 영어가 아닌 짧은 시맨틱 ID(t.rich)
// → 영어 원문은 아래 // i18n-en: 주석으로 준다 (build-en 이 이 주석을 en 값으로 사용)
// i18n-en: Users added <emphasized>for the first time are WS Admin.</emphasized>
{t.rich("AddToWorkspaceRoleInfoBanner", { emphasized: c => <b>{c}</b> })}
```

`en.json`, `ko.json`, `ja.json`과 TSV를 손으로 고치는 일, 시트에 접근하는 일, 키를 시트에 올리는 일은 스크립트와 CI가 맡으므로 **개발자가 하지 않아도 됩니다.**

---

## 5. 번역자는 ko/ja 채우고 버튼 누르면 끝

번역자 쪽은 더 단순합니다.

1. `i18n_translations` 탭에서만 작업합니다.
2. `en` 컬럼을 참고해 **`ko`, `ja` 컬럼만** 채웁니다. `key`와 `en`은 건드리지 않습니다.
3. 비워 두면 화면에는 영어로 나옵니다. 채운 것만 번역으로 반영됩니다.
4. 작업이 끝나면 "번역 완료" 버튼(또는 시트 상단 i18n 메뉴의 `번역 완료 → PR 생성`)을 누릅니다. 잠시 뒤 GitHub에 sync PR이 올라옵니다.

리치 텍스트 키는 `<emphasized>…</emphasized>`, `<br></br>` 같은 **태그 이름을 그대로 두고**, 그 안의 단어와 어순만 번역합니다.

## 6. 관리자가 할 일은 세팅과 검수

1. 처음 한 번, 시트에 `i18n_dev_inbox`, `i18n_translations` 탭을 만들고 repo의 현재 번역으로 채운 뒤 env를 설정합니다.
2. GitHub도 한 번 설정합니다. 레포 Settings의 Actions 설정에서 "Allow GitHub Actions to create and approve pull requests"를 켜고 write 권한을 줍니다(sync PR용). Secrets에는 `GOOGLE_SHEETS_SPREADSHEET_ID`, `GOOGLE_APPLICATION_CREDENTIALS`를 등록합니다.
3. 평소에는 "번역 완료" 버튼이 올린 **sync PR을 검수한 뒤 머지**합니다. 급하면 GitHub Actions에서 `i18n pull` 워크플로를 수동으로 실행합니다.
4. Figma의 영어 원문을 `t()`로 코드에 넣는 것도 관리자의 몫입니다.

## 7. 엔진 ① 코드가 키를 나른다 (스크립트)

개발자와 번역자, 관리자의 일이 이만큼 줄어든 건 사람이 하던 일을 스크립트가 맡았기 때문입니다. 명령은 모두 `pnpm i18n:*` 또는 `pnpm messages:*`이고, 시트에 쓰는 명령은 해당 탭 env가 없으면 건너뜁니다(기본 시트 오염 방지).

### 키 추출 (`extract-keys.mjs`)

`src/**`의 `t()`, `t.rich()` 호출을 긁어 `{ key, en }` 목록을 만듭니다. 키를 정확히 뽑아야 해서 호출 위치만 보고 네임스페이스를 정하지 않습니다.

- 변수 바인딩으로 네임스페이스를 찾습니다. `const t = useTranslations("A")`와 `const tForgot = useTranslations("B")`를 추적해, 각 호출이 쓴 변수의 네임스페이스를 정확히 매칭합니다. 한 파일에 네임스페이스가 여러 개인 경우가 전체 파일의 30%라 이게 필요했습니다.
- `t.rich`도 포함하고, `// i18n-en:` 주석(시맨틱 키의 영어 원문)도 파싱합니다.
- `t("Don't…")`, `t("… \"x\" …")`처럼 따옴표와 이스케이프가 든 문자열도 잘리지 않게 정규식으로 캡처합니다.

동작은 3단계입니다. 바인딩을 모으고, 리터럴 호출을 모은 뒤, 각 호출을 같은 변수의 직전 바인딩 네임스페이스로 매칭합니다.

```javascript
// ── 3종 정규식으로 스캔 (읽기용 단순화; 실제는 따옴표, 이스케이프까지 처리) ──
// ① 바인딩:  const t = useTranslations("NS")  → { 변수명, 네임스페이스 }
// ② 리터럴:  t("Edit chart") / t.rich("…")     (obj.t(…) 은 제외)
// ③ 동적:    t(변수)  → 그 네임스페이스를 "동적"으로 표시(prune 이 통째 보호)

// 파일마다: bindings[] 수집 → calls[], annotations[] 수집 → 아래처럼 매칭
for (const call of calls) {
  // 이 호출의 네임스페이스 = "같은 변수의 직전(위치) 바인딩"
  // (한 파일에 const t=…, const tErr=… 여러 개여도 정확)
  let binding = null;
  for (const b of bindings) {
    if (b.name === call.name && b.pos < call.pos) {
      if (binding == null || b.pos > binding.pos) binding = b;
    }
  }
  const key = binding.ns === "" ? call.arg : `${binding.ns}.${call.arg}`;
  // en: 호출 바로 윗줄 `// i18n-en:` 주석이 있으면 그 값, 없으면 leaf(=영어 원문)
  const en = annotated ? annotation.text : leafOf(key);
  entries.push({ key, en, annotated }); // → build-en 이 이 목록으로 en.json 생성
}
```

### 코드에서 en.json 만들기 (`build-en.mjs`)

```javascript
pnpm i18n:build-en           # en.json 갱신
pnpm i18n:build-en --check   # 누락만 검사(쓰기 X), CI 게이트
pnpm i18n:build-en --watch   # 파일 저장 감지 → 자동 갱신 (dev watcher 가 이걸 띄움)
pnpm i18n:build-en --prune   # ⚠️ raw prune: orphan 전부 삭제 → 동적 키까지 날림. 직접 쓰지 말 것(안전판은 아래 i18n:prune)
```

- 신규 키는 leaf(또는 주석) 값으로 채웁니다.
- 기존 값은 그대로 둡니다. `Loading`으로 들어간 값을 `Loading...`으로 다듬어 두었다면 덮어쓰지 않습니다.
- 주석이 있으면 그 값이 우선입니다.
- 내용이 같으면 파일을 쓰지 않습니다(write-if-changed). 그래서 watcher가 dev 서버를 괜히 리로드하지 않습니다.
- orphan(코드에 없는 키)은 기본적으로 남겨 둡니다(9장 참고).

```javascript
// src/ 전체를 돌면서 파일마다 extractEntriesFromText를 호출하고, 결과를 key 기준으로 합쳐 dedupe한 뒤 정렬해서 반환하는 함수
export async function extractTranslationEntriesFromSrc() {
  const files = await collectSourceFiles(SRC);
  /** @type {Map<string, { key: string; en: string; annotated: boolean }>} */
  const byKey = new Map();
  for (const file of files) {
    const text = await readFile(file, "utf-8");
    for (const entry of extractEntriesFromText(text)) {
      const existing = byKey.get(entry.key);
      if (existing == null) {
        byKey.set(entry.key, entry);
        continue;
      }
      if (!existing.annotated && entry.annotated) {
        byKey.set(entry.key, entry);
      }
    }
  }
  return Array.from(byKey.values()).sort((a, b) => a.key.localeCompare(b.key));
}

export function flattenMessages(obj, prefix = "") {
  /** @type {Record<string, string>} */
  const out = {};
  for (const [segment, value] of Object.entries(obj)) {
    const key = prefix === "" ? segment : `${prefix}.${segment}`;
    if (typeof value === "object" && value !== null && !Array.isArray(value)) {
      Object.assign(out, flattenMessages(value, key));
      continue;
    }
    out[key] = value == null ? "" : String(value);
  }
  return out;
}
/*
{
  "LlmEval": {
    "CriteriaBenchmark": {
      "VersionHistory": {
        "Edit Description": "Edit Description",
        "Restore": "Restore"
      }
    }
  }
->
{
  "LlmEval.CriteriaBenchmark.VersionHistory.Edit Description": "Edit Description",
  "LlmEval.CriteriaBenchmark.VersionHistory.Restore": "Restore",
}
*/

async function collectSourceFiles(dir, out = []) {
  const entries = await readdir(dir, { withFileTypes: true });
  for (const e of entries) {
    const full = path.join(dir, e.name);
    if (e.isDirectory()) {
      if (SKIP_DIR.has(e.name)) {
        continue;
      }
      await collectSourceFiles(full, out);
    } else if (
      e.isFile() &&
      /\.(tsx|ts)$/.test(e.name) &&
      !/\.test\.(tsx|ts)$/.test(e.name)
    ) {
      out.push(full);
    }
  }
  return out;
}
```

`en.json`을 실제로 쓰는 건 아래 `buildOnce`입니다. 기존 값을 보존하고, 신규 키를 채우고, 내용이 바뀔 때만 파일을 씁니다.

```javascript
async function buildOnce({ prune }) {
  const entries   = await extractTranslationEntriesFromSrc(); // 코드의 {key,en,annotated}
  const codeByKey = new Map(entries.map(e => [e.key, e]));
  const existing  = await readEnFlat();                       // 기존 en.json(평탄화)

  const result = [];
  // 1) 기존 키: 순서, 값 보존. annotated 면 주석 값 우선. prune 이면 orphan 은 버림
  for (const [key, value] of Object.entries(existing)) {
    const code = codeByKey.get(key);
    if (code == null) { if (!prune) result.push({ key, en: value }); continue; }
    result.push({ key, en: code.annotated ? code.en : value });
  }
  // 2) 신규 키: leaf(또는 주석)로 시드
  for (const e of entries) if (!(e.key in existing)) result.push({ key: e.key, en: e.en });

  // 3) 내용이 바뀔 때만 쓴다 (write-if-changed → dev 불필요 리로드 방지)
  const next = stringifyMessages(rowsToNestedObjects(result, ["en"]).en);
  if (next !== await readFile(EN_PATH, "utf-8").catch(() => "")) {
    await writeFile(EN_PATH, next, "utf-8");
  }
}

// --watch: src/ 변경 감지 → 300ms 디바운스 후 buildOnce 재실행 (dev watcher 가 띄움)
watch(srcDir, { recursive: true }, (_event, filename) => {
  if (!/\.(tsx|ts)$/.test(String(filename))) return;
  clearTimeout(timer);
  timer = setTimeout(() => buildOnce({ prune }), 300);
});

/*
input: const t = useTranslations("LlmEval.Criteria");
// i18n-en: Cancel
<button>{t("Cancel")}</button>
{t("Save")}

output: Promise<{ key: string; en: string; annotated: boolean }[]>
*/
```

### dev junk만 안전하게 제거 (`prune-unused-keys.mjs`)

`build-en --prune`이 orphan을 전부 지우는 것과 달리, 개발 중에 넣었다가 안 쓰게 된 키만 골라 지웁니다. pre-commit에서 자동으로 실행되고, 아래 4조건을 **모두** 만족해야 지웁니다.

1. 현재 `en.json`에 있음
2. 코드에서 리터럴 `t()`로 쓰지 않음
3. base(`origin/qa`, `I18N_PRUNE_BASE`로 변경 가능)의 `en.json`에 없음. 이번 브랜치가 새로 넣은 키라는 뜻
4. 동적 네임스페이스가 아님. `t(변수)` 호출이 있는 네임스페이스(예: `VersionHistory`) 아래는 통째로 보호

`--dry-run`으로 제거 후보만 미리 볼 수 있고, base를 못 읽으면 prune을 건너뜁니다(커밋은 막지 않습니다). base(origin/qa)는 git 로컬 ref에서 읽으므로 네트워크를 쓰지 않습니다.

```javascript
// base(origin/qa) 의 en.json 키 (git 로컬 ref 에서 읽음)
function baseEnKeys() {
  try {
    const raw = execFileSync("git", ["show", `${BASE_REF}:messages/en.json`]);
    return new Set(Object.keys(flattenMessages(JSON.parse(raw))));
  } catch { return null; } // ref 없으면 null → prune 자체 skip(커밋 안 막음)
}

const currentFlat = flattenMessages(JSON.parse(await readFile(EN_PATH)));
const codeKeys    = new Set(await extractTranslationKeysFromSrc());    // 코드 리터럴 t("…")
const baseKeys    = baseEnKeys();                                      // origin/qa
const dynamicNs   = [...(await extractDynamicNamespacesFromSrc())];    // t(변수) 있는 방
const isDynamic   = key => dynamicNs.some(ns => key === ns || key.startsWith(`${ns}.`));

// 제거 대상 = 4조건 전부: en.json에 있음 ∧ 코드에 없음 ∧ base에 없음 ∧ 동적 방 아님
const targets = Object.keys(currentFlat).filter(
  key => !codeKeys.has(key) && !baseKeys.has(key) && !isDynamic(key),
);
// dry-run 이면 targets 목록만 출력, 아니면 targets 를 뺀 나머지로 en.json 재작성
```

### 코드에서 Dev Inbox로 (`push-keys-to-sheet.mjs`)

신규 키를 `(key, en)`으로 `i18n_dev_inbox`에 append합니다. en 컬럼에 원문을 넣고 ko/ja는 빈칸으로 둡니다. 추가만 하므로(add-only) 기존 행은 건드리지 않고, `GOOGLE_SHEETS_DEV_TAB`이 없으면 건너뜁니다. 값은 `RAW`로 써서 `+ Add Data`처럼 +로 시작하는 문구가 수식으로 읽히지 않게 합니다.

const entries  = await extractTranslationEntriesFromSrc();          // 코드의 {key, en}

const toAdd    = entries.filter(e => !existing.has(e.key));         // 새 키만

  if (enIndex > 0) row[enIndex] = e.en;          // en 컬럼만 시드 (ko/ja 는 빈칸)
  return row;
});

await sheets.spreadsheets.values.append({

### Dev Inbox에서 Translations로 (`promote-keys-to-translations.mjs`)

Dev Inbox에 있고 Translations에 없는 키만 `i18n_translations`로 append합니다. 그래서 번역자 탭에는 번역할 새 키만 덧붙습니다. 두 탭의 컬럼 순서가 다를 수 있어서, 컬럼 위치 대신 헤더 이름으로 맞춰 재배열합니다.

const translationKeys = new Set(trans.dataRows.map(r => String(r[0]).trim()));

// Dev Inbox 행 → 헤더명 기준 레코드 → Translations 에 없는 key 만

### Translations에서 ko/ja.json으로 (`pull-sheet-to-messages.mjs`)

`i18n_translations`의 ko/ja만(빈 셀 제외) 읽어 `ko.json`, `ja.json`을 생성하고, `translations.tsv`는 en(코드)과 ko/ja(시트)를 합친 스냅샷으로 재생성합니다. `en`은 코드가 주인이라 여기서는 절대 쓰지 않습니다. 빈 칸은 런타임에 영어로 폴백되니 굳이 넣지 않습니다.

```javascript
// ko/ja.json: 비어있지 않은 셀만 (미번역 키는 생략 → 런타임에 en 폴백)
for (const locale of translatedLocales) {            // ["ko", "ja"] (en 제외)

    .filter(r => String(r[locale] ?? "").trim() !== "")
    .map(r => ({ key: r.key, [locale]: r[locale] }));

// en.json 은 절대 안 씀(코드 소유). tsv 는 en(코드)+ko/ja(시트) 스냅샷으로 재생성.
```

### dev에서 저장하면 자동 반영 (`instrumentation-i18n-watch.ts`)

`pnpm dev`로 서버가 뜰 때 Next의 `register()` 훅이 dev이면서 Node 런타임일 때만 watcher 모듈을 동적 import합니다. node 전용 코드(`node:child_process`)를 별도 모듈로 분리한 이유는, `instrumentation.ts`가 Edge 런타임용으로도 번들되는데 node API를 직접 두면 Edge 빌드가 깨지기 때문입니다(Sentry가 `sentry.server.config`를 동적 import하는 패턴과 같습니다).

```typescript
// instrumentation.ts: dev+node 에서만 watcher 를 동적 import (Edge 안전)
export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    await import("../sentry.server.config");
    if (process.env.NODE_ENV === "development") {
      await import("./instrumentation-i18n-watch");
    }
  }
  if (process.env.NEXT_RUNTIME === "edge") await import("../sentry.edge.config");
}
```

```typescript
// instrumentation-i18n-watch.ts: build-en --watch 를 dev 서버의 자식으로 실행
import { spawn } from "node:child_process";
const g = globalThis as typeof globalThis & { __i18nBuildEnWatcher?: boolean };
if (!g.__i18nBuildEnWatcher) {            // 중복 spawn 방지 (HMR 재실행 대비)
  g.__i18nBuildEnWatcher = true;
  const child = spawn(process.execPath, ["scripts/i18n/build-en.mjs", "--watch"], {
    stdio: "inherit", cwd: process.cwd(),
  });
  const stop = () => child.kill();        // dev 서버 죽으면 같이 종료
  process.once("exit", stop);
  process.once("SIGINT", () => { stop(); process.exit(0); });
  process.once("SIGTERM", () => { stop(); process.exit(0); });
}
```

`t("New copy")`를 저장하면 watcher가 `en.json`을 갱신하고 dev 서버가 hot-reload합니다. prod와 edge에서는 아무 일도 하지 않습니다.

## 8. 엔진 ② 전 과정을 자동화한다 (CI + 버튼)

사람이 기억해서 돌려야 하는 명령이 하나라도 남으면, 언젠가 빠뜨립니다. 그래서 각 시점마다 무엇이 도는지를 못 박아 두었습니다.

| 시점 | 동작 | 네트워크 |
| --- | --- | --- |
| 저장 (dev) | watcher가 `build-en --watch`로 en.json 자동 갱신 | 없음 (오프라인) |
| 커밋 | pre-commit이 `build-en`, `prune`(dev junk 제거) 순으로 en.json 갱신 | 없음 (오프라인) |
| qa/main 머지 | `i18n-sync.yml`이 push-keys, promote 순으로 실행 | 필요 (secret은 CI) |
| 번역 완료 버튼 | `i18n-pull.yml`이 pull 후 sync PR 생성 | 필요 |
| PR (CI) | `ci.yml`의 `build-en --check` 검사 (merge 조건) | 없음 |
| 빌드/배포 | 커밋된 JSON 사용 | 없음 |

### 워크플로

- `.github/workflows/i18n-sync.yml`: `main`/`qa`에 `push`될 때(paths: src, en.json, scripts/i18n) `push-keys`와 `promote`를 돌립니다. 탭 이름 기본값은 `vars.* || 'i18n_dev_inbox'`입니다.
- `.github/workflows/i18n-pull.yml`: `repository_dispatch: i18n-translations-ready`와 `workflow_dispatch`에서 `pull`한 뒤 `peter-evans/create-pull-request`로 PR을 냅니다. 브랜치 `i18n/sync-translations`를 재사용하므로 버튼을 여러 번 눌러도 같은 PR이 갱신됩니다.
- `ci.yml`: 기존 라이브 pull을 없애고 `i18n:build-en --check`로 바꿨습니다(커밋된 `en.json`이 코드와 맞는지 검증).

### 시트 헬퍼가 미번역과 PascalCase를 강조한다 (Apps Script)

번역자가 시트에서 바로 확인할 수 있게, "번역 완료" 버튼과 같은 Apps Script 프로젝트에 헬퍼 메뉴를 달아 두었습니다. 헤더명(`key`/`ko`/`ja`) 기준이라 컬럼 순서와 상관없고, 지금 보고 있는 탭에 적용됩니다.

- "미번역(빈칸) 강조"는 빈 `ko`/`ja` 셀을 노란색으로 칠해, 무엇을 번역해야 하는지 한눈에 보이게 합니다.
- "PascalCase 키 강조"는 leaf가 영어가 아닌 키(PascalCase/camel/SCREAMING)를 빨간색으로 칠합니다. 코드 쪽 `pnpm i18n:audit-keys`의 시트 버전입니다.
- "강조 지우기"는 칠한 색을 지웁니다.

```javascript
function onOpen() {
  SpreadsheetApp.getUi().createMenu("🌐 i18n")
    .addItem("번역 완료 → PR 생성", "notifyTranslationsReady")
    .addSeparator()
    .addItem("미번역(빈칸) 강조", "highlightUntranslated")
    .addItem("PascalCase 키 강조", "highlightPascalKeys")
    .addItem("강조 지우기", "clearI18nHighlights")
    .addToUi();
}

function i18nColumns_(sheet) {
  const header = sheet.getRange(1, 1, 1, sheet.getLastColumn()).getValues()[0];
  const idx = name => header.findIndex(h => String(h).trim().toLowerCase() === name) + 1;
  return { key: idx("key"), en: idx("en"), ko: idx("ko"), ja: idx("ja") };
}

function highlightUntranslated() {
  const sheet = SpreadsheetApp.getActiveSheet();
  const cols = i18nColumns_(sheet);
  const lastRow = sheet.getLastRow();
  if (lastRow < 2) return;
  for (const col of [cols.ko, cols.ja]) {
    if (col < 1) continue;
    const range = sheet.getRange(2, col, lastRow - 1, 1);
    const bg = range.getValues().map(([v]) => [String(v ?? "").trim() === "" ? "#fff3cd" : null]);
    range.setBackgrounds(bg);
  }
}

function looksLikeNonEnglishLeaf_(key) {
  const s = String(key);
  const leaf = s.includes(".") ? s.split(".").pop() : s;
  if (leaf.indexOf(" ") !== -1) return false;
  return /[a-z][A-Z]/.test(leaf) || leaf.indexOf("_") !== -1 || /^[A-Z][A-Z0-9]{3,}$/.test(leaf);
}

function highlightPascalKeys() {
  const sheet = SpreadsheetApp.getActiveSheet();
  const cols = i18nColumns_(sheet);
  const lastRow = sheet.getLastRow();
  if (lastRow < 2 || cols.key < 1) return;
  const range = sheet.getRange(2, cols.key, lastRow - 1, 1);
  const bg = range.getValues().map(([v]) => [looksLikeNonEnglishLeaf_(v) ? "#f8d7da" : null]);
  range.setBackgrounds(bg);
}

function clearI18nHighlights() {
  const sheet = SpreadsheetApp.getActiveSheet();
  const lastRow = sheet.getLastRow();
  if (lastRow < 2) return;
  sheet.getRange(2, 1, lastRow - 1, sheet.getLastColumn()).setBackground(null);
}
```

## 9. 정적 추출이 못 보는 키

코드가 더 이상 안 쓰는데 `en.json`이나 시트에 남은 키를 orphan이라 부릅니다. orphan이라고 다 같지는 않습니다. 진짜 죽은 키도 있지만, **정적 추출이 못 볼 뿐 멀쩡히 살아 있는 키**도 orphan처럼 보입니다. 이 둘을 구분하지 못하면 청소하려다 살아 있는 키를 지워 화면을 깨뜨립니다.

갈림길은 네임스페이스(= `useTranslations("...")`에 넘기는 접두사)의 성격입니다.

- 일반(정적) 네임스페이스는 키가 항상 리터럴(`t("Edit chart")`)입니다. 추출기가 소스만 읽어도 쓰는 키를 100% 다 보므로, 여기의 orphan은 진짜 죽은 키입니다.
- 동적 네임스페이스에는 `t(변수)` 호출이 하나라도 있습니다. 변수 값은 `SourceTypeEdited` 같은 enum 식별자이거나, `t(LABEL_KEY[x])`처럼 맵으로 푸는 영어 구문(`Average score`, 페이지 헤더 제목, 메트릭 라벨 등)입니다. 추출기는 `t(변수)`라는 호출만 볼 뿐 어떤 키로 풀리는지 모르므로, 이 네임스페이스의 orphan은 살아 있을 수 있습니다. 그래서 통째로 보호합니다.

> **`build-en --prune`을 직접 쓰지 마세요.** 동적 호출의 키(예: `SELF_EVALUATION`, `SourceTypeEdited`)는 정적 추출이 못 봅니다. 추출기가 못 찾았다고 죽은 키는 아닙니다. 전부 삭제하면 살아 있는 동적 키가 날아가 화면이 깨집니다.

그래서 pre-commit에는 `i18n:prune`을 연결했습니다. 7장에서 본 4조건을 모두 만족해야 지우므로, 개발 중에 넣었다가 안 쓰게 된 키(dev junk)만 사라지고 기존 키와 동적 네임스페이스 키는 건드리지 않습니다.

> 처음에는 동적 네임스페이스라도 여러 단어로 된 키는 지우는 휴리스틱을 넣었다가, `PageHeaders` 제목, `Metrics` 라벨처럼 맵으로 푸는 살아 있는 다중 단어 키가 지워질 수 있어 철회했습니다. 동적 네임스페이스의 키는 모양만으로 구분할 수 없으니, 통째로 보호하는 게 맞았습니다.

> 이 위험은 실제로 드러났습니다. 처음에는 안전장치로 세 번째 조건(base diff)만 뒀는데, `--dry-run`을 돌리니 제거 후보에 `SourceTypeEdited`, `SourceTypeFileUploaded`(동적 `t(variant.messageKey)` 키)가 떴습니다. base(origin/qa)에 아직 없던 신규 동적 키라 base diff를 통과해 버린 것입니다. 그대로 지웠으면 버전 히스토리 태그가 깨졌을 겁니다. 그래서 네 번째 조건인 동적 네임스페이스 보호를 추가해, `t(변수)`가 있는 네임스페이스는 통째로 빼는 이중 안전장치를 걸었습니다.

여기서 권장 사항이 하나 나왔습니다. 동적 dispatch는 전용 네임스페이스에 둡니다. `t(변수)`를 정적 라벨과 같은 네임스페이스에 두면 그 네임스페이스 전체가 보호돼 죽은 정적 키가 쌓입니다. dispatch를 좁은 하위 네임스페이스(`…VersionHistory.Source`)로 분리하면 보호 범위가 그만큼 좁아지고, 나머지 키는 `i18n:prune`의 정리 대상으로 돌아옵니다(Cursor와 Claude용 규칙 `next-intl.mdc`에 MUST로 적어 두었습니다).

참고로 orphan은 UI를 깨뜨리지 않습니다(영어 폴백). `i18n:prune`이 못 지우는 건 동적 네임스페이스 안의 죽은 키(안전을 위해 보존)와 base에 이미 있던 오래된 죽은 키뿐이고, 이런 키는 진짜 죽은 것만 골라 수동으로 지웁니다. `en.json`에서 키를 지우고, tsv를 재생성한 뒤, 시트에서 행을 삭제합니다.

## 10. 개선 후 달라진 모습들

- 개발자가 `t("...")`만 써도 저장하는 순간 `en.json`이 채워집니다(dev watcher). 손으로 JSON 세 개를 만질 일이 없어졌습니다.
- 번역자는 시트만 봅니다. `i18n_translations` 탭에서 ko/ja를 채우고 "번역 완료" 버튼을 누르면 잠시 뒤 sync PR이 올라옵니다.
- 한 셀의 주인이 하나뿐이라 같은 값을 두고 충돌할 일이 없고, 락도 머지 전략도 필요 없습니다.
- `pull`은 ko/ja만 가져오고 `en`은 시트에서 내려오지 않아서, 영어가 ko/ja로 역류할 경로가 없습니다. 영어 회귀를 되돌리던 응급 스크립트도 이제 필요 없습니다.
- 미번역 키가 있어도 런타임에 영어로 폴백되니 화면이 깨지지 않고, 배포는 라이브 fetch 없이 커밋된 JSON만 씁니다.

## 11. 이 설계가 치른 대가

leaf = 영어 원문 컨벤션이 가장 비쌉니다. 2장의 이 원칙 위에 파이프라인 전체가 서 있지만, 대가가 하나 따라옵니다. **키가 곧 영어 문장이라, 영어를 고치면 키가 바뀝니다.** `Save changes`를 `Save`로 줄이는 순간 그건 새 키이고, 기존 ko/ja 번역은 옛 키에 붙은 채 orphan이 됩니다. 화면은 안 깨집니다(영어 폴백). 대신 조용히 영어로 돌아갑니다.

카피를 자주 다듬는 팀이라면 이건 결정적인 비용입니다. 반대로 문구가 안정적이라면 거의 드러나지 않습니다. 이 설계는 영어 원문이 자주 바뀌지 않는다는 데 베팅한 셈입니다. 그 전제가 깨지면 키를 의미 기반 ID(`btn.save`)로 바꾸고 `en.json`도 사람이 관리하는, 훨씬 평범한 구조로 돌아가야 합니다.

동적 네임스페이스를 통째로 보호하면 그 안의 죽은 키는 자동으로 지워지지 않습니다. 9장에서 `t(변수)`가 하나라도 있는 네임스페이스는 전체를 보호하기로 했으니, 그 안의 진짜 죽은 키도 그대로 남습니다. 안전을 택한 대신 쓰레기가 쌓이는 구조입니다. 지금은 수동 제거로 버티고 있지만, 네임스페이스가 커지면 감당이 안 될 겁니다. 그래서 dispatch를 좁은 하위 네임스페이스로 분리하라는 규칙을 MUST로 박아뒀는데, 이 규칙은 사람이 지켜야 동작하는 안전장치이고 구조로 해결한 건 아닙니다.

시트가 단일 장애점입니다. 번역 흐름 전체가 스프레드시트 하나와 Apps Script에 걸려 있습니다. 시트 권한이 꼬이면 번역자는 작업할 수 없고, Apps Script가 멈추면 버튼으로 PR을 올릴 수 없습니다. 개발자 쪽은 시트 없이도 `t()`만으로 돌아가니 반쪽은 살아 있지만, 처음부터 노린 건 아니고 소유권을 나눈 데서 따라온 부수 효과입니다.

## 12. 그냥 번역 관리 SaaS를 쓰면 되지 않나

당연히 나올 질문이고, 대부분의 경우 맞는 말입니다. Crowdin이나 Lokalise 같은 도구는 여기서 직접 만든 것을 전부 제품으로 제공합니다. 키 추출, 시트 동기화, 번역 완료 알림, 미번역 폴백까지.

직접 만들어서 얻은 것과 잃은 것이 함께 있습니다.

| 직접 구축 | 번역 SaaS |
| --- | --- |
| 키 컨벤션을 우리 코드에 맞게 정함 | 도구의 키 모델을 따라야 함 |
| 동적 네임스페이스 보호 같은 우리만의 규칙을 넣을 수 있음 | 도구가 지원하는 범위 안에서만 |
| 비용 0 (시트 + Actions) | 좌석/키 개수 기반 과금 |
| 파이프라인이 깨지면 내가 고쳐야 함 | 벤더가 고침 |
| 번역자가 익숙한 스프레드시트를 그대로 씀 | 번역자가 새 도구를 배워야 함 |

개인적인 의견이지만, 갈림길은 **번역자가 누구인가**라고 봅니다. 전문 번역 벤더가 붙는다면 SaaS 쪽이 낫습니다. TM(번역 메모리), 용어집, 리뷰 워크플로 같은 걸 직접 만들 이유가 없으니까요. 반대로 사내 인원이 스프레드시트로 채우는 규모라면, 도구를 새로 배우게 하는 비용이 만드는 비용보다 클 수 있습니다.

## 13. 마치며

작업하고 나서 생각이 바뀐 게 하나 있습니다.

처음에는 이걸 i18n 문제라고 생각했습니다. 다국어를 어떻게 잘 관리하느냐. 그런데 끝내고 보니 **소유권 문제**였습니다. 락도, 머지 전략도, 응급 복구 스크립트도 전부 두 주체가 같은 값을 쓴다는 전제 위에서 사후 수습하는 도구입니다. 전제를 바꾸니 도구가 전부 필요 없어졌습니다.

같은 모양을 다른 데서도 봅니다. 캐시 무효화가 어려운 건 원본과 사본에 주인이 둘이기 때문이고, 머지 충돌이 잦은 건 한 파일에 여러 사람이 쓰기 때문입니다. 해결책이 늘 소유권 분리인 건 아니지만, "이걸 어떻게 잘 합칠까" 대신 "애초에 왜 둘이 쓰지"를 한 번 물어볼 가치는 있다고 생각합니다.

이번에는 그 질문 하나 덕분에 응급 스크립트를 지웠습니다.

남은 일은 운영하며 규칙을 다듬는 것입니다. 특히 11장에서 짚은 leaf 컨벤션의 비용이 실제로 얼마나 아픈지, 카피를 몇 번 고쳐보면 알게 될 것 같습니다.

## 부록. 흔한 실패

- `translations.tsv`에서 머지 충돌이 나면 손으로 맞추지 말고 JSON에서 재생성합니다. `en/ko/ja.json`이 깨끗이 머지됐다면 TSV는 그 결과물이므로, `messages:sync-tsv`(또는 같은 방식의 재생성)를 돌린 뒤 `git add`하면 끝입니다. 실제 qa 머지 때 이렇게 해결했습니다.
- 시트에 의도하지 않은 키가 잔뜩 올라가는 문제는, push-keys가 기본 시트로 가지 않도록 `GOOGLE_SHEETS_DEV_TAB`을 필수로 두고 pre-commit에서 push-keys를 빼서(오프라인 build-en만) 막았습니다.
- `PERMISSION_DENIED`가 나면 서비스 계정 `client_email`을 스프레드시트에 편집자로 공유했는지 확인합니다.
- 번역이 화면에 안 보이면 아직 ko/ja에 없는 키입니다. 영어 폴백이 동작하는 정상 상태이고, 번역한 뒤 pull하면 반영됩니다.
