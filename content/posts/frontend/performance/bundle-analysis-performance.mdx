`@next/bundle-analyzer`를 처음 열었을 때가 기억납니다. 알록달록한 트리맵이 뜨고, 마우스를 올리면 크기가 나옵니다. 그리고 거기서 멈췄습니다.

가장 큰 사각형의 이름은 `static/chunks/3463.7a4bde….js`였습니다. 콘텐츠 해시라 코드가 바뀌면 이름도 바뀝니다. 안에 뭐가 들었는지는 확대해서 하나씩 짚어봐야 알 수 있고, 짚어봤자 이걸 어떻게 줄일지는 여전히 제 몫이었습니다. 도구는 무엇이 큰지는 알려주는데 무엇을 할지는 알려주지 않았습니다.

그래서 리포트를 하나 만들었습니다. 청크 안에 뭐가 들었는지 이름으로 보여주고, 항목마다 줄이는 방법을 붙이고, PR마다 자동으로 돕니다.

## 1. 트리맵으로는 다음 행동이 안 나온다

트리맵은 비율을 보는 도구이고, 제가 필요했던 건 할 일 목록이었습니다. 구체적으로 세 군데서 막혔습니다.

청크 이름에 정보가 없습니다. `3463.7a4bde….js`가 8.9%를 차지한다는 걸 알아도, 그게 차트 라이브러리인지 폼 라이브러리인지 알려면 확대해서 들여다봐야 합니다. 리포트를 팀에 공유해도 받은 사람이 같은 작업을 반복합니다.

큰 파일과 여러 번 실려 나가는 파일이 섞입니다. 30KB짜리 컴포넌트 하나와, 3KB짜리인데 12개 라우트에 중복 포함돼 36KB를 차지하는 유틸은 완전히 다른 문제입니다. 앞은 코드 분할로 풀고, 뒤는 공통 청크 설정이나 import 경로로 풉니다. 그런데 트리맵에서는 둘 다 그냥 사각형입니다.

손댈 수 있는 것과 없는 것이 갈리지 않습니다. 랭킹 1위가 `next`였습니다. 628KB. 프레임워크는 직접 줄이기 어렵습니다. 이런 항목이 위에 있으면 목록 전체가 무의미해 보입니다.

## 2. 세 가지 축으로 쪼갠 랭킹

같은 번들을 세 방향에서 봅니다. 방향마다 고칠 방법이 다르기 때문입니다.

| 섹션 | 보는 단위 | 답하는 질문 |
| --- | --- | --- |
| Packages | `node_modules`의 라이브러리 | 남의 코드 중 뭐가 자리를 먹나 |
| First-party | `src/` 아래 직접 작성한 파일 | 우리 코드 중 뭐가 무거운가 |
| Chunks | 브라우저가 실제로 내려받는 `.js` 파일 | 이 파일 안에 뭐가 들었나 |

앞의 둘은 내용물이고 마지막은 포장 단위입니다. 브라우저가 받는 건 청크인데 제가 고칠 수 있는 건 내용물이라, 둘을 따로 봐야 합니다.

### 청크에 `What's inside`를 넣은 이유

청크 이름은 버렸습니다. 대신 그 안에서 크기를 가장 많이 차지하는 3개를 이름으로 적습니다.

```text
✗ static/chunks/3463.7a4bde….js    623 KB
✓ 623 KB: echarts (345 KB), zrender (171 KB), recharts (74.3 KB) 외 5개
```

파일명을 볼 이유가 없어집니다. 3장에서 차트 라이브러리가 두 개 들어 있는 걸 발견한 것도 이 열 덕분입니다.

### Size와 Shipped를 나눈 이유

총량은 비슷한데 처방이 다른 두 경우가 있습니다.

**경우 A. 청크 1개에 들어간 30KB짜리 차트 렌더러**

파일이 그냥 큽니다. 대시보드를 열지도 않는 사용자까지 이걸 받습니다. 그래서 `next/dynamic`으로 미룹니다.

**경우 B. 청크 12개에 들어간 3KB짜리 로깅 유틸**

파일은 작은데 라우트 청크 12개에 각각 복사본이 들어가서, 빌드 전체로는 36KB가 나갑니다.

```text
logger.ts (3KB)
  ├─ chunk-dashboard.js   ← 복사본
  ├─ chunk-settings.js    ← 복사본
  ├─ chunk-billing.js     ← 복사본
  └─ … 총 12부
```

복사되는 이유는 webpack이 여러 청크가 함께 쓰는 모듈을 공통 청크로 끌어올릴지 말지를 크기와 참조 수 임계값으로 정하기 때문입니다. 작은 파일은 그 임계값에 못 미쳐서 각 청크에 인라인되는 쪽으로 갑니다.

청크 12개는 라우트 경계 때문에 이미 나뉘어 있던 것이고, logger는 그 안에 하나씩 복사된 것입니다.

사용자 입장에서는 `/dashboard`에서 `/settings`로 이동할 때 같은 코드를 또 받습니다. 파일이 다르니 브라우저 캐시도 소용이 없습니다. 그래서 공통 청크로 올리거나 import 경로를 정리합니다. 여기서 `dynamic`은 도움이 안 됩니다. 12군데서 각자 필요해서 들어간 거니까요.

`Shipped`는 크기 순으로는 눈에 안 띄는 파일을 잡는 열입니다. `Size` 순으로 정렬하면 3KB짜리 logger는 30KB짜리 차트 렌더러보다 한참 아래에 있습니다. 총량은 logger가 더 큰데도요. 트리맵에서도 3KB 사각형 12개로 흩어져 있어서 합이 36KB라는 사실이 어디에도 안 나타납니다.

반대로 36KB를 사용자 한 명이 받는 양으로 읽으면 과대평가입니다. 한 라우트만 보고 나가면 3KB만 받습니다. `Shipped`는 이 파일이 캐시를 타지 못하고 반복해서 내려가고 있다는 신호로 읽어야 합니다.

| 열 | 뜻 | 경우 A | 경우 B |
| --- | --- | --- | --- |
| `Size` | 파일 원본 한 부 | 30KB | 3KB |
| `Shipped` | 빌드에 실제로 실린 총량 | 30KB | 36KB |
| `Chunks` | 몇 개 청크에 들어갔나 | 1 | 12 |

`Shipped ÷ Size`가 곧 몇 부 복사됐는지입니다. 경우 A는 1배, 경우 B는 12배입니다.

### Advice는 if-then 목록입니다

조건에 맞으면 정해진 문구가 붙습니다.

| 조건 | 붙는 Advice |
| --- | --- |
| 차트, 에디터처럼 무거운 라이브러리인데 청크 하나에만 들어감 | `next/dynamic`으로 지연 로드 |
| 유틸리티인데 여러 청크에 중복 | per-path import로 바꾸거나 공통 청크로 올리기 |
| 같은 패키지의 버전이 두 개 | `pnpm dedupe` |

**per-path import**는 패키지를 루트로 부르는 대신 필요한 파일 경로로 바로 import하는 방식입니다.

```js
import { debounce } from 'lodash'        // barrel 경유: 약 70KB
import debounce from 'lodash/debounce'   // per-path: 약 2KB
```

루트로 부르면 번들러가 그 패키지의 `index.js`를 평가합니다. 그게 전부 re-export하는 barrel이고 트리셰이킹이 안 되는 패키지라면, 안 쓰는 것까지 딸려옵니다. per-path는 index를 건너뛰고 파일 하나로 갑니다.

**`pnpm dedupe`**는 같은 패키지가 두 버전으로 설치돼 번들에 두 벌 들어갈 때 씁니다. 내 앱은 `zod@^4.4`를 쓰는데 어떤 라이브러리가 `zod@^4.1`을 요구하는 경우가 그렇습니다. 둘 다 4.4로 만족되는데도 따로 설치되면, dedupe가 lockfile을 다시 풀어 하나로 합칩니다. zod가 151KB라면 151KB를 통째로 줄이는 셈입니다. 다만 범위가 진짜 호환되지 않으면(`^3` vs `^4`) 못 합칩니다. 그땐 `overrides`로 강제하거나 의존하는 쪽을 올려야 합니다.

세 규칙 모두 코드를 읽지 않고 이름과 숫자만 보고 붙습니다. 그래서 틀릴 때가 있습니다(7장).

## 3. 만들고 나서 처음 찾은 것

리포트를 처음 돌렸을 때 나온 상위 청크입니다.

```text
| # | Chunk                        | Type   | Parsed | Gzip   | %    | What's inside (top)                                           |
| 1 | static/chunks/3463.7a4bde…js | shared | 623 KB | 209 KB | 8.9% | echarts (345 KB), zrender (171 KB), recharts (74.3 KB) 외 5개  |
| 2 | static/chunks/9615-775d55…js | shared | 546 KB | 159 KB | 7.8% | @base-ui/react (202 KB), zod (151 KB), @tanstack/table-core (47.5 KB) 외 16개 |
```

1번 청크의 `What's inside`를 보고 바로 알았습니다. **차트 라이브러리가 두 개 들어 있었습니다.**

패키지 랭킹에서 확인하니 더 분명해졌습니다.

```text
| # | Package  | Parsed | Gzip   | %    | Versions | Chunks | Advice                                              |
| 1 | next     | 628 KB | 256 KB | 9.0% | 16.1.6   | 12     | 프레임워크 기본: 직접 줄이기 어렵습니다               |
| 3 | echarts  | 345 KB | 133 KB | 4.9% | 6.1.0    | 1      | next/dynamic(ssr:false) + echarts/core 부분 import   |
| 4 | recharts | 282 KB | 117 KB | 4.0% | 3.8.1    | 2      | 차트 라이브러리 통일 검토 (echarts와 공존)            |
```

echarts 345KB에 그 의존성인 zrender 171KB, 여기에 recharts 282KB. 합치면 parsed 798KB입니다. 차트 라이브러리 두 벌이 번들에 같이 실려 있었던 겁니다.

처음엔 두 라이브러리가 서로 다른 시점에 다른 화면을 만들면서 들어왔을 거라고 짐작했습니다. 각자의 시점에서는 합리적인 선택이었을 거라고요. git log를 보니 틀렸습니다. echarts와 recharts는 **같은 날, 같은 커밋**(2026-03-05, 레포 초기 구축)에 함께 들어왔습니다. 처음부터 둘 다 있었던 겁니다. 그래도 결론은 같습니다. 청크 이름이 해시로만 보이는 동안에는 이 둘이 한 청크에 같이 실린다는 사실이 눈에 띄지 않았습니다.

우리 코드 쪽 상위는 이랬습니다.

```text
| # | Module                          | Size    | Shipped | Gzip    | Chunks | Advice                              |
| 1 | …/DashboardChartRenderer.tsx    | 30.3 KB | 30.3 KB | 11.3 KB | 1      | 모달/오버레이: 열릴 때만 dynamic     |
| 2 | src/shared/ui/Table/Table.tsx   | 23.1 KB | 23.1 KB | 8.1 KB  | 1      | 큰 컴포넌트: 초기 렌더 필요성 확인    |
```

여기서는 `Size == Shipped`라 중복 문제는 없었습니다. 그냥 큰 컴포넌트입니다. 중복 배수가 큰 건 오히려 로깅 유틸처럼 작고 여기저기 쓰이는 파일들이었는데, `Size` 순 정렬에서는 아래쪽에 있어 눈에 안 띕니다. 정렬 축 하나로는 부족했고, 그래서 리포트 아래쪽에 중복 항목만 따로 뽑은 표를 붙였습니다.

## 4. 크기 다음은 체감 속도

번들 크기는 대리 지표입니다. 사용자가 느끼는 건 화면이 언제 뜨느냐죠. 그래서 라우트별 Core Web Vitals를 같이 재서 리포트에 합쳤습니다.

```text
| Route            | LCP     | CLS   | TBT    | FCP    | SI      | Total Bytes |
| /sign-in         | 1507 ms | 0.000 | 0 ms   | 903 ms | 2652 ms | 1,417,455   |
| /user-management | 5406 ms | 0.000 | 276 ms | 905 ms | 905 ms  | 1,854,642   |
| /workspace-info  | 5706 ms | 0.000 | 268 ms | 904 ms | 904 ms  | 1,851,827   |
```

LCP 판정 기준은 2.5초 이하가 good, 4초 초과가 poor입니다. 두 인증 페이지가 5.4초와 5.7초, 둘 다 poor입니다.

여기서 두 리포트가 이어집니다. `/workspace-info`가 부르는 청크를 랭킹에서 찾으면 3장의 그 차트 청크가 나옵니다. 623KB를 초기 로드에 싣고 있으니 LCP를 늦추는 원인으로 먼저 의심할 만합니다. **무거운 청크와 느린 페이지가 같은 곳을 가리킬 때** 우선순위가 정해집니다.

측정은 라우트당 3회를 돌려 median run만 저장합니다. 1회 측정은 사람을 속입니다. 나중에 랜딩 리다이렉트를 수정 전후로 비교할 때, 수정 후 빌드의 1회차 성능 점수만 82가 나오고 2~5회차는 전부 90이었습니다. standalone 서버의 첫 요청 워밍업이었는데, 1회만 봤으면 개선폭을 절반으로 적었을 겁니다([그 측정 기록](/blog/frontend/performance/landing-redirect-lcp)).

인증이 필요한 라우트는 로그인하지 않으면 `/sign-in`으로 리다이렉트됩니다. 그래서 측정 전에 NextAuth API로 로그인하고, 받은 세션 쿠키를 넣은 상태로 재도록 했습니다. 인증을 건너뛰는 데모 계정용 경로는 만들지 않았습니다. 실제 백엔드를 거치는 시간까지 측정값에 들어가야 한다고 봤기 때문입니다.

## 5. PR마다 자동으로 돌리기

리포트가 아무리 좋아도 사람이 기억해서 돌려야 하면 안 돌아갑니다. GitHub Actions에 붙였습니다.

- PR을 열거나 업데이트하면 자동 실행
- 번들 랭킹 상위 15개 패키지와 권고, 중복 버전, Lighthouse 결과를 **스티키 코멘트**로 게시
- 전체 리포트는 아티팩트로 업로드
- 라우트를 지정해 수동으로도 돌릴 수 있음

스티키 코멘트로 한 건 의도적입니다. PR이 업데이트될 때마다 새 코멘트가 쌓이면 잘 안 보게 됩니다. 코멘트 하나를 계속 덮어써서 지금 이 브랜치의 번들 상태만 보이게 했습니다.

## 6. 이 도구가 못 하는 것

webpack 빌드가 필요합니다. 번들 통계를 뽑으려면 `next build --webpack`을 돌려야 하고, Turbopack 개발 서버를 쓰다가 분석할 때만 webpack으로 다시 빌드하니 수 분이 걸립니다. 캐시된 통계로 랭킹만 다시 만드는 경로를 따로 뒀지만, 분석 대상 빌드와 실제 배포 빌드가 다를 수 있다는 문제는 남습니다. 지금은 프로덕션도 webpack이라 괜찮지만, Turbopack으로 넘어가면 이 도구는 다시 만들어야 합니다.

헤드리스 측정은 껍데기를 잴 수 있습니다. 인증 페이지의 데이터가 SSR에 의존할 때, 헤드리스 환경에서는 데이터가 덜 채워진 상태로 측정되는 경우가 있습니다. 위 표의 5.7초는 인증된 페이지의 껍데기 기준으로는 유효하지만, 실제 사용자가 데이터까지 다 받는 시점은 그보다 늦을 겁니다. 이 수치는 하한선으로 봐야 합니다.

INP는 아예 못 잽니다. INP는 실제 사용자 인터랙션이 있어야 나오는 지표라 합성 측정으로는 안 나오고, 위 표에 INP가 없는 것도 그래서입니다. 합성 측정 자체의 한계라 RUM(실사용자 모니터링)을 따로 붙이지 않는 한 계속 비어 있을 겁니다.

> **후기 (2026-09):** INP는 두 갈래로 채웠습니다. 랩에서는 Playwright로 실제 클릭을 넣고 `PerformanceEventTiming`을 페이지 안에서 수집해 입력 지연, 처리, 페인트로 쪼개 보는 하네스를 만들었고, 필드는 Sentry Web Vitals가 받아옵니다. INP가 비어 있던 이유는 짐작대로 합성 측정의 한계였고, 도구를 바꿀 필요 없이 인터랙션을 직접 넣으면 됐습니다.

`Versions` 열에는 노이즈가 섞입니다. 중복 버전을 세면 156개가 나오는데, 열어보면 `@esbuild/darwin-arm64`(0.27.7, 0.28.1)나 `@emnapi/runtime`(1.9.2, 1.10.0, 1.11.1) 같은 빌드 타임 도구가 대부분입니다. 브라우저에 안 나가니 dedupe해도 번들은 그대로입니다. 실제로 번들에 들어간 패키지만 세도록 걸러야 하는데 지금은 안 걸러져 있습니다.

측정 환경이 개발자 랩탑입니다. CI에서 도는 값과 제 맥북에서 도는 값이 다릅니다. 절대값보다 같은 환경에서의 추이를 봐야 합니다.

## 7. 자동 권고는 어디까지 믿을 만한가

Advice 열을 규칙 기반으로 자동 생성했다고 했는데, 이게 틀릴 때가 있습니다. 예를 들어 차트 라이브러리를 `next/dynamic`으로 지연 로드하라는 권고는 대체로 맞지만, 그 차트가 대시보드 첫 화면의 주요 콘텐츠라면 지연 로드가 오히려 LCP를 악화시킵니다. 규칙은 그 맥락을 모릅니다.

실제로 틀리는 예가 코드베이스에 있습니다. `date-fns`를 barrel로 import하는 곳이 여섯 군데 있는데, 규칙대로면 "per-path import로 바꾸라"가 붙을 자리입니다. 그런데 이 패키지는 이렇습니다.

```json
// node_modules/date-fns/package.json
{ "version": "4.4.0", "type": "module", "sideEffects": false }
```

`sideEffects: false`이고 ESM이라, 루트에서 import해도 번들러가 안 쓰는 걸 전부 털어냅니다. per-path로 바꿔봤자 이득이 없습니다. lodash 시절에 맞던 처방이 지금 패키지에는 안 맞는 건데, 규칙은 그 차이를 볼 수 없습니다. 판단하려면 이름이나 크기 대신 그 패키지의 `sideEffects` 플래그를 봐야 하거든요.

더 나쁜 건 **틀린 권고가 맞는 권고와 똑같은 톤으로 적혀 있다는 것**입니다. 표 안에 같은 서식으로 나란히 있으니 다 검증된 것처럼 읽히고, 읽는 사람은 규칙이 확신할 수 있는 항목과 그렇지 않은 항목을 구분할 방법이 없습니다.

그럼 자동 권고를 아예 빼는 게 나았을까요. 개인적인 의견이지만, 아닙니다. 권고가 없으면 리포트를 잘 안 보게 됩니다. 숫자만 있는 표는 "그래서 뭘 하라고"에서 다시 막히고, 그게 애초에 이 도구를 만든 이유였습니다. 틀릴 수 있는 제안이라도 있는 편이 아무 제안도 없는 것보다 사람을 움직입니다.

date-fns 사례를 겪고 나서, 규칙의 오류에도 종류가 있다는 걸 알았습니다. 규칙의 판단은 셋으로 갈립니다.

| | 예 | 어떻게 할까 |
| --- | --- | --- |
| 지금도 맞게 판단 | 중복 버전, 중복 배수(`Shipped ÷ Size`) | 그대로 단정해서 적는다 |
| 할 수 있는데 안 하고 있음 | 패키지의 `sideEffects` 읽기, 번들에 실제로 들어가는지 거르기 | 규칙을 고치면 없어지는 오류다 |
| 자동으로는 못 함 | 첫 화면 콘텐츠인가, 라이브러리를 교체할 가치가 있나, 팀이 그 리팩터링을 감당하나 | 단정하지 말고 질문으로 적는다 |

date-fns 오류는 두 번째 줄입니다. 규칙이 `package.json`의 `sideEffects`를 읽게 하면 사라집니다. 반면 차트가 첫 화면 콘텐츠인지는 세 번째 줄이라, 규칙을 아무리 정교하게 만들어도 판단할 수 없습니다.

처음엔 이 둘을 뭉뚱그려 "규칙은 원래 부정확하다"고 넘겼는데, 그건 게으른 결론이었습니다. **고칠 수 있는 오류를 못 고치는 오류로 분류해두면 영영 안 고칩니다.**

AI로 심층 리포트를 붙인 것도 같은 맥락입니다. 랭킹 JSON과 Lighthouse 결과를 읽어 실제 import 위치까지 짚어주는 단계를 하나 더 뒀는데, 규칙이 못 보는 맥락(어느 라우트에서 부르는지, 첫 화면인지)을 코드를 읽어서 채우라는 의도였습니다. 다만 이것도 검증 없이 믿을 물건은 아닙니다. 후보를 좁혀주는 용도로 보는 게 맞다고 생각합니다.

## 8. 예산이 없으면 랭킹도 소용없다

만들고 나서 제일 아쉬운 건, 랭킹은 있는데 기준선이 없다는 것입니다.

지금 리포트는 무엇이 큰지를 순서대로 보여줍니다. 그런데 그게 문제인지 아닌지는 알려주지 않습니다. 차트 청크 623KB가 큰 건 맞는데, 큰 게 곧 나쁜 건 아닙니다. 대시보드 제품에서 차트는 주요 기능이니까요. 판단하려면 초기 로드 예산을 gzip 기준 몇 KB로 둘지 먼저 합의해야 하는데, 그게 없으니 매번 감으로 판단하고 있습니다.

그래서 랭킹을 더 다듬기보다 번들 예산을 먼저 붙이려고 합니다. 라우트별로 상한을 정하고, PR에서 넘으면 실패시키는 것. 그러면 리포트를 읽는 사람이 없어도 규칙이 대신 막아줍니다.

> **후기 (2026-08):** 예산은 붙였습니다. `perf-budget.json`에 기본 상한(LCP 6,000ms / 총 2MB)과 라우트별 오버라이드를 두고 PR마다 검사합니다. 다만 아직 **막지는 않습니다.** CI 스텝이 `continue-on-error: true`라 초과하면 `::warning::`만 남습니다. 이유는 기준치입니다. 실측에서 workspace-info가 LCP 8.3초라 6초 기준을 그대로 강제하면 PR이 바로 빨개지고, 그러면 팀은 이 검사를 끄고 싶어집니다. 라우트별 기준을 실측값에 맞춰 확정한 뒤 막는 단계로 올리는 게 순서라고 보고 경고 단계에 두었습니다.

돌아보면 순서가 반대였습니다. 측정 도구를 먼저 만들고 기준을 나중에 찾고 있는데, 기준을 먼저 정했으면 도구가 훨씬 단순해졌을 겁니다. 예산이 있으면 랭킹 전체가 필요 없고 "넘었는가 / 넘었으면 어디 때문인가" 두 줄이면 되니까요.
