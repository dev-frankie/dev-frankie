`@next/bundle-analyzer`를 처음 열었을 때가 기억납니다. 알록달록한 트리맵이 뜨고, 마우스를 올리면 크기가 나옵니다. 그리고 거기서 멈췄습니다.

가장 큰 사각형의 이름은 `static/chunks/3463.7a4bde….js`였습니다. 콘텐츠 해시라 빌드할 때마다 바뀝니다. 안에 뭐가 들었는지는 확대해서 하나씩 짚어봐야 알 수 있고, 짚어봤자 "이걸 어떻게 줄이지"는 여전히 제 몫이었습니다. 도구는 **무엇이 큰지**는 알려주는데 **무엇을 할지**는 안 알려줬습니다.

그래서 리포트를 하나 만들었습니다. 청크 안에 뭐가 들었는지 이름으로 보여주고, 항목마다 줄이는 방법을 붙이고, PR마다 자동으로 도는 것. 이 글은 그걸 만든 과정과, 만들고 나서 찾은 것들입니다. 마지막에는 이런 자동 권고가 어디까지 믿을 만한지도 짚습니다.

## 1. 트리맵으로는 다음 행동이 안 나온다

번들 분석기가 안 좋다는 게 아닙니다. 목적이 다릅니다. 트리맵은 **비율을 보는 도구**고, 제가 필요했던 건 **할 일 목록**이었습니다.

구체적으로 세 가지가 막혔습니다.

**청크 이름에 정보가 없다.** `3463.7a4bde….js`가 8.9%를 차지한다는 걸 알아도, 그게 차트 라이브러리인지 폼 라이브러리인지 알려면 확대해서 들여다봐야 합니다. 리포트를 팀에 공유해도 다들 같은 작업을 반복합니다.

**"큰 파일"과 "많이 실려나가는 파일"이 섞인다.** 30KB짜리 컴포넌트 하나와, 3KB짜리인데 12개 라우트에 중복 포함돼 36KB를 차지하는 유틸은 완전히 다른 문제입니다. 앞은 코드 분할로 풀고, 뒤는 공통 청크 설정이나 import 경로로 풉니다. 그런데 트리맵에서는 둘 다 그냥 사각형입니다.

**손댈 수 있는 것과 없는 것이 안 갈린다.** 랭킹 1위가 `next`였습니다. 628KB. 프레임워크를 줄일 수는 없습니다. 이런 항목이 위에 있으면 목록 전체가 무의미해 보입니다.

## 2. 세 가지 축으로 쪼갠 랭킹

그래서 리포트를 세 섹션으로 나눴습니다. 각 섹션이 다른 질문에 답합니다.

| 섹션 | 답하는 질문 | 정렬 축 | 마지막 열 |
| --- | --- | --- | --- |
| First-party Modules | 내가 쓴 코드 중 뭐가 무거운가 | 단일 사본 크기(Size) | Advice |
| Packages | 어떤 라이브러리가 자리를 먹나 | 총 크기 | Advice + 중복 버전 |
| Chunks | 이 파일 안에 뭐가 들었나 | 청크 크기 | What's inside |

핵심은 두 가지입니다.

**Chunks에 `What's inside` 열을 넣은 것.** 청크 이름은 버리고, 그 안에서 가장 큰 기여자 3개를 이름으로 적습니다. 파일명을 볼 이유가 없어집니다.

**First-party에서 `Size`와 `Shipped`를 분리한 것.** `Size`는 단일 사본 크기, `Shipped`는 실제로 번들에 실려나간 총량입니다. `Shipped ÷ Size`가 곧 중복 배수입니다. `Chunks` 열까지 같이 보면 몇 군데에 중복됐는지 바로 나옵니다.

Advice는 규칙 기반으로 붙였습니다. 정교하지 않습니다. "차트/에디터류 + 단일 청크 → `next/dynamic`", "유틸리티 + 다중 청크 → per-path import", "버전이 2개 → `pnpm dedupe`" 같은 패턴 매칭입니다. 이 선택의 대가는 7장에서 다시 다룹니다.

## 3. 만들고 나서 처음 찾은 것

리포트를 처음 돌렸을 때 나온 상위 청크입니다.

```text
| # | Chunk                        | Type   | Parsed | Gzip   | %    | What's inside (top)                                           |
| 1 | static/chunks/3463.7a4bde…js | shared | 623 KB | 209 KB | 8.9% | echarts (345 KB), zrender (171 KB), recharts (74.3 KB) 외 5개  |
| 2 | static/chunks/9615-775d55…js | shared | 546 KB | 159 KB | 7.8% | @base-ui/react (202 KB), zod (151 KB), @tanstack/table-core (47.5 KB) 외 16개 |
```

1번 청크의 `What's inside`를 보고 바로 알았습니다. **차트 라이브러리가 두 개 들어 있었습니다.**

패키지 랭킹에서 확인하니 더 분명해졌습니다.

```text
| # | Package  | Parsed | Gzip   | %    | Versions | Chunks | Advice                                              |
| 1 | next     | 628 KB | 256 KB | 9.0% | 16.1.6   | 12     | 프레임워크 기본 — 직접 줄이기 어렵습니다              |
| 3 | echarts  | 345 KB | 133 KB | 4.9% | 6.1.0    | 1      | next/dynamic(ssr:false) + echarts/core 부분 import   |
| 4 | recharts | 282 KB | 117 KB | 4.0% | 3.8.1    | 2      | 차트 라이브러리 통일 검토 (echarts와 공존)            |
```

echarts 345KB에 그 의존성인 zrender 171KB, 여기에 recharts 282KB. 합치면 **parsed 798KB**입니다. 전체 번들의 상당 부분을 차트가 두 벌 차지하고 있었던 겁니다.

이건 누가 잘못한 게 아닙니다. 두 라이브러리는 서로 다른 시점에, 서로 다른 화면을 만들면서 들어왔을 겁니다. 각자의 시점에서는 합리적인 선택이었을 테고요. 문제는 **두 선택이 만나는 지점을 볼 방법이 없었다는 것**입니다. 청크 이름이 해시였으니까요.

[확인필요: 각각 언제·어느 화면 때문에 들어왔는지 git log로 확인하면 이 문단이 추측이 아니라 사실이 됩니다]

내 코드 쪽 상위는 이랬습니다.

```text
| # | Module                          | Size    | Shipped | Gzip    | Chunks | Advice                              |
| 1 | …/DashboardChartRenderer.tsx    | 30.3 KB | 30.3 KB | 11.3 KB | 1      | 모달/오버레이 — 열릴 때만 dynamic    |
| 2 | src/shared/ui/Table/Table.tsx   | 23.1 KB | 23.1 KB | 8.1 KB  | 1      | 큰 컴포넌트 — 초기 렌더 필요성 확인   |
```

여기서는 `Size == Shipped`라 중복 문제는 없었습니다. 단순히 큰 컴포넌트입니다. 중복 배수가 큰 건 오히려 로깅 유틸처럼 작고 여기저기 쓰이는 파일들이었습니다. `Size` 순 정렬에서는 아래쪽에 있어 눈에 안 띕니다. **정렬 축 하나로는 부족하다**는 게 여기서 드러났고, 그래서 중복 항목만 따로 뽑은 표를 아래에 붙였습니다.

## 4. 크기 다음은 체감 속도

번들 크기는 대리 지표입니다. 사용자가 느끼는 건 화면이 언제 뜨느냐죠. 그래서 라우트별 Core Web Vitals를 같이 재고 리포트에 병합했습니다.

```text
| Route            | LCP     | CLS   | TBT    | FCP    | SI      | Total Bytes |
| /sign-in         | 1507 ms | 0.000 | 0 ms   | 903 ms | 2652 ms | 1,417,455   |
| /user-management | 5406 ms | 0.000 | 276 ms | 905 ms | 905 ms  | 1,854,642   |
| /workspace-info  | 5706 ms | 0.000 | 268 ms | 904 ms | 904 ms  | 1,851,827   |
```

LCP 판정 기준은 2.5초 이하가 good, 4초 초과가 poor입니다. 두 인증 페이지가 5.4초와 5.7초, 둘 다 poor입니다.

여기서 두 리포트가 이어집니다. `/workspace-info`가 부르는 청크를 랭킹에서 찾으면 3장의 그 차트 청크가 나옵니다. 623KB를 초기 로드에 물고 있으니 LCP가 늦는 게 당연합니다. **"어떤 청크가 무거운가"와 "어떤 페이지가 느린가"가 같은 원인을 가리킬 때** 비로소 우선순위가 정해집니다.

측정은 라우트당 3회를 돌려 median run만 저장합니다. Core Web Vitals는 노이즈가 커서 1회 측정은 사람을 속입니다.

[확인필요: 1회 측정과 median의 편차를 실제로 겪은 사례가 있으면 여기에 수치를 넣으면 좋습니다. 없으면 이 문단은 이대로 둡니다]

인증이 필요한 라우트는 로그인 월에 막혀 `/sign-in`으로 리다이렉트됩니다. 그래서 측정 전에 NextAuth API로 로그인해 세션 쿠키를 재생한 뒤 측정하도록 했습니다. 데모 계정 바이패스는 만들지 않았습니다. 실제 백엔드를 타는 게 측정값에 포함되어야 한다고 봤기 때문입니다.

## 5. PR마다 자동으로 돌리기

리포트가 아무리 좋아도 사람이 기억해서 돌려야 하면 안 돌아갑니다. GitHub Actions에 붙였습니다.

- PR 생성·업데이트 시 자동 실행
- 번들 랭킹 상위 15개 패키지 + 권고 + 중복 버전, Lighthouse 결과를 **스티키 코멘트**로 게시
- 전체 리포트는 아티팩트로 업로드
- 라우트를 지정한 수동 실행도 가능

스티키 코멘트로 한 건 의도적입니다. PR마다 새 코멘트가 쌓이면 아무도 안 봅니다. 하나를 계속 덮어써서 "지금 이 브랜치의 번들 상태"만 보이게 했습니다.

## 6. 이 도구가 못 하는 것

**webpack 빌드를 강제합니다.** 번들 통계를 뽑으려면 `next build --webpack`이 필요합니다. Turbopack 개발 서버를 쓰다가 분석할 때만 webpack으로 다시 빌드해야 하니 수 분이 걸립니다. 캐시된 통계로 랭킹만 재생성하는 경로를 따로 뒀지만, 근본적으로는 **분석 대상 빌드와 실제 배포 빌드가 다를 수 있다**는 문제가 남습니다. 지금은 프로덕션도 webpack이라 괜찮지만, Turbopack으로 넘어가면 이 도구는 다시 만들어야 합니다.

**헤드리스 측정은 껍데기를 잴 수 있습니다.** 인증 페이지의 데이터가 SSR에 의존적일 때, 헤드리스 환경에서는 데이터가 덜 채워진 상태로 측정되는 경우가 있습니다. 위 표의 5.7초는 "인증된 페이지 셸" 기준으로는 유효하지만, 실제 사용자가 데이터까지 다 받는 시점은 그보다 늦을 겁니다. **이 수치는 하한선입니다.**

**INP는 아예 못 잽니다.** 표의 INP 열이 전부 비어 있는 게 그 이유입니다. INP는 실제 사용자 인터랙션이 있어야 나오는 지표라 합성 측정으로는 안 나옵니다. 이건 도구의 한계가 아니라 합성 측정 자체의 한계고, RUM(실사용자 모니터링)을 따로 붙이지 않는 한 계속 비어 있을 겁니다.

**측정 환경이 개발자 랩탑입니다.** CI에서 도는 값과 제 맥북에서 도는 값이 다릅니다. 절대값을 신뢰할 게 아니라 **같은 환경에서의 추이**만 봐야 합니다.

## 7. 자동 권고는 어디까지 믿을 만한가

여기서부터는 만들고 나서 생각이 바뀐 부분입니다.

Advice 열을 규칙 기반으로 자동 생성했다고 했는데, 이게 **틀릴 때가 있습니다.** 예를 들어 "차트 라이브러리 → `next/dynamic`으로 지연 로드"는 대체로 맞지만, 그 차트가 대시보드의 첫 화면 핵심 콘텐츠라면 지연 로드가 오히려 LCP를 악화시킵니다. 규칙은 그 맥락을 모릅니다.

더 나쁜 건 **틀린 권고가 맞는 권고와 똑같은 톤으로 적혀 있다는 것**입니다. 표 안에 나란히 있으면 다 검증된 것처럼 읽힙니다. 규칙이 확신할 수 있는 항목과 그렇지 않은 항목이 같은 서식으로 나열되니, 읽는 사람이 구분할 방법이 없습니다.

[확인필요: Advice를 그대로 적용했다가 되돌린 사례가 실제로 있었다면 여기에 넣으면 이 논지가 훨씬 강해집니다]

그럼 자동 권고를 아예 빼는 게 나았을까요. 개인적인 의견이지만, 아닙니다. 권고가 없으면 리포트를 아무도 안 봅니다. 숫자만 있는 표는 "그래서 뭘 하라고"에서 다시 막히고, 그게 애초에 이 도구를 만든 이유였습니다. **틀릴 수 있는 제안이라도 있는 편이, 아무 제안도 없는 것보다 행동을 유발합니다.**

대신 이렇게 정리했습니다.

| 자동으로 판단 가능 | 사람이 판단해야 |
| --- | --- |
| 중복 버전 (`Versions`가 2개 이상) | 지연 로드해도 되는가 (첫 화면 콘텐츠인가) |
| 중복 배수 (`Shipped ÷ Size`) | 라이브러리를 교체할 가치가 있는가 |
| per-path import 가능 여부 (패키지 구조) | 팀이 그 리팩터링을 감당할 수 있는가 |

왼쪽은 규칙으로 확정할 수 있고, 오른쪽은 못 합니다. **왼쪽만 단정하고 오른쪽은 질문 형태로 적는 게** 지금 찾은 절충입니다.

AI로 심층 리포트를 붙인 것도 같은 맥락입니다. 랭킹 JSON과 Lighthouse 결과를 읽어 실제 import 위치까지 짚어주는 단계를 하나 더 뒀는데, 이건 규칙이 못 보는 맥락(어느 라우트에서 부르는지, 첫 화면인지)을 코드를 읽어서 채우라는 의도였습니다. 다만 이것도 검증 없이 믿을 물건은 아닙니다. **후보를 좁혀주는 용도**로 보는 게 맞다고 생각합니다.

## 8. 예산이 없으면 랭킹도 소용없다

만들고 나서 제일 아쉬운 건, 랭킹은 있는데 **기준선이 없다는 것**입니다.

지금 리포트는 "무엇이 큰가"를 순서대로 보여줍니다. 그런데 이게 문제인지 아닌지는 안 알려줍니다. 차트 청크 623KB가 큰 건 맞는데, 큰 게 곧 나쁜 건 아닙니다. 대시보드 제품에서 차트는 핵심 기능이니까요. 판단하려면 "우리 초기 로드 예산은 gzip 기준 몇 KB"라는 합의가 먼저 있어야 하는데, 그게 없으니 매번 감으로 판단하고 있습니다.

그래서 다음에 붙일 건 랭킹의 정교화가 아니라 **번들 예산**입니다. 라우트별로 상한을 정하고, PR에서 넘으면 실패시키는 것. 그러면 리포트를 읽는 사람이 없어도 규칙이 대신 막아줍니다.

돌아보면 순서가 반대였습니다. 측정 도구를 먼저 만들고 기준을 나중에 찾고 있는데, 기준을 먼저 정했으면 도구가 훨씬 단순해졌을 겁니다. 예산이 있으면 랭킹 전체가 필요 없고 "넘었는가 / 넘었으면 어디 때문인가" 두 줄이면 되니까요.

측정은 쉽고 기준은 어렵습니다. 그리고 어려운 쪽이 먼저였습니다.
