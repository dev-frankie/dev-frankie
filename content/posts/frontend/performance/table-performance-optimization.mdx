> **테이블 성능 측정 시리즈**
> - **1편 (이 글)** — 무엇을 알아냈고, 무엇이 틀렸나
> - [2편 — Playwright로 프론트엔드 성능을 재는 하네스 만들기](./table-performance-measurement): navMs·scrollMs·domRows를 어떻게 뽑았나

수백 컬럼에 깊게 중첩된 평가 테이블이 있습니다. 첫 진입도 스크롤도 버벅일 만한 구조라 Prefetch와 Virtualization을 적용했고, 정말 효과가 있는지 Playwright로 쟀습니다.

결과는 좋았습니다. 진입 체감 32% 개선, DOM 행 수 46 → 18로 61% 감소. 두 번째 숫자를 성과로 적었습니다.

두 달 뒤에 이런 지적을 받았습니다. **"겨우 46행 렌더링하던 걸 가상화했다고요? 이거 최적화 맞아요?"** 맞는 지적이었습니다. 이 글은 그 첫 측정과, 지적을 받고 합성 데이터로 다시 쟀을 때 나온 결과, 그리고 무엇을 철회했는지에 대한 기록입니다. 측정 하네스를 어떻게 만들었는지는 [2편](./table-performance-measurement)에 있습니다.

> **1차 측정** 2026-06-17 · localhost → QA API · Playwright E2E + User Timing API
> 케이스당 5회 median · 총 80샘플 · 약 9.4분
>
> **재측정** 2026-08-01 · Storybook + 합성 데이터 · Playwright + CDP

## 1. 무엇을 재려 했나

우리 서비스에는 LLM 성능 측정을 위한 평가 데이터를 볼 수 있는 **평가 디테일 페이지**가 있습니다. 적게는 수십 개에서 많게는 수백 개의 컬럼으로 이루어진 테이블이고, 여러 단계로 깊게 중첩된(depth가 큰) 데이터 구조를 가지고 있습니다.

이런 데이터를 테이블로 그대로 그리면, 첫 진입 시점이나 스크롤할 때 병목이 걸릴 수 있습니다. 그렇다면 이를 어떻게 풀어야 할까요? 저는 **TanStack Query의 Prefetch**와 **TanStack Table의 가상화(Virtualization)** 를 적용했습니다. 이 글은 그 두 가지가 정말 체감 성능에 영향을 주는지 수치로 측정한 기록입니다.

구체적으로는 목록에서 **Run 확장 → Task 클릭 → Task Results 테이블 준비 완료**까지의 체감 성능을 비교했습니다.

**비교 축**

- **Prefetch ON/OFF** — Run expand / Task link hover 시 React Query prefetch
- **Virtualize ON/OFF** — Task Results 테이블 가상 스크롤 (TanStack Table)

**배경** — 평가 Run 1건을 조회하려면 7-way 조인이 필요해 목록·상세 응답이 느렸고, lazy load + prefetch + virtualize로 개선한 뒤 수치로 검증했습니다.

**핵심 지표 3가지** (1샘플당 Playwright가 수집)

| 지표 | 한 줄 정의 | 유저 관점 |
| --- | --- | --- |
| **navMs** | Task 클릭 → Results 테이블 준비 완료까지 ms | "Task 눌렀을 때 얼마나 빨리 표가 뜨나?" — **진입 체감 속도** |
| **scrollMs** | 테이블 맨 위→맨 아래 1회 스크롤 소요 ms | "긴 표를 끝까지 내릴 때 버벅이나?" — **스크롤 반응성** |
| **domRows** | 스크롤 후 DOM에 실제로 그려진 `tbody tr` 개수 | 직접 체감 지표는 아니고, **virtualize가 DOM을 얼마나 줄였는지** 확인용 |

## 2. 결론부터 — 그리고 그중 하나는 틀렸다

> **최적 조합 (4케이스 평균):** prefetch ON + virtualize ON → nav **323ms** (baseline 472ms 대비 **약 32%↓**)
>
> **Virtualize 효과:** 케이스 A DOM **46행 → 18행** (약 61%↓) — 이 숫자는 *가상화가 동작한다*는 증거일 뿐 성능 개선 근거가 아닙니다. 아래 6절에서 철회했습니다.
>
> **Prefetch 최대 개선:** 케이스 B nav **623ms → 148ms** (OFF+OFF vs ON+ON)

### 시나리오별 평균 (4 URL median 평균)

표의 **navMs**는 prefetch 효과(데이터 미리 받기)를, **domRows**는 virtualize 효과(DOM 행 수)를 읽을 때 봅니다. **scrollMs**는 행이 적을 때 virtualize ON이 오히려 높게 나올 수 있습니다(아래 §5 참고).

| **시나리오** | **Prefetch** | **Virtualize** | **평균 navMs** | **평균 scrollMs** | **한줄 요약** |
| --- | --- | --- | --- | --- | --- |
| prefetch-on_virtualize-on | ON | ON | **323** | 35 | 평균 nav 최저 · DOM 절감 |
| prefetch-on_virtualize-off | ON | OFF | 393 | **17** | scroll 최저 · DOM 최대 |
| prefetch-off_virtualize-on | OFF | ON | 422 | 30 | 중간 |
| prefetch-off_virtualize-off | OFF | OFF | 472 | **17** | baseline · nav 최고 |

## 3. 어떻게 쟀나 (요약)

측정 하네스 구축은 [2편](./table-performance-measurement)에서 코드까지 다룹니다. 여기서는 숫자를 읽는 데 필요한 만큼만 짚습니다.

**4-way 조합을 URL 플래그로 갈랐습니다.** `?benchPrefetch=&benchVirtualize=` 쿼리로 두 기능을 각각 켜고 끄면, 같은 빌드에서 네 시나리오를 순회할 수 있습니다. 별도 브랜치를 파지 않아도 됩니다.

**타이밍은 앱 안에서, 판정은 앱 밖에서.** 클릭 시점과 테이블 준비 완료 시점에 User Timing API로 마크를 찍고, Playwright가 그 값을 읽어갑니다. Playwright가 직접 시간을 재면 드라이버 왕복이 섞입니다.

**케이스당 5회를 돌려 median만 씁니다.** 총 80샘플, 9.4분. 이 표본 크기가 나중에 한계로 돌아옵니다(5.5절).

| 지표 | 무엇을 재나 | 어떻게 |
| --- | --- | --- |
| `navMs` | Task 클릭 → Results 테이블 준비 완료 | User Timing mark 2개 사이 |
| `scrollMs` | 테이블 맨 위 → 맨 아래 1회 스크롤 | 프로그램 스크롤 소요 시간 |
| `domRows` | 스크롤 후 DOM에 실제로 그려진 `tbody tr` | `querySelectorAll` 카운트 |

측정용 임시 코드는 측정이 끝난 뒤 제거했습니다. 프로덕션 최적화 코드(prefetch·virtualization)만 남아 있습니다.

## 5. 숫자가 말한 것

### 5.1 지표별 해석

| 지표 | 이번 측정에서 본 것 | 판단 |
| --- | --- | --- |
| **navMs** | 4케이스 평균 **472ms → 323ms** (prefetch ON + virtualize ON). 케이스 B **623ms → 148ms** | Prefetch + hydration이 **진입 체감**에 가장 큰 기여. 케이스·캐시 상태에 따라 편차 있음 |
| **scrollMs** | 대부분 **17ms 전후** (virtualize OFF). ON은 **27~52ms** (행 많은 케이스) | 현재 데이터 규모에선 scroll 자체는 빠름. virtualize ON은 스크롤 벤치에 약간의 오버헤드가 있을 수 있으나 **domRows 절감**과 트레이드오프 |
| **domRows** | 케이스 A **46 → 18** (61%↓), 케이스 B **30 → 19** | 가상화가 **동작한다는 증거**일 뿐, 이 규모에서 성능 개선 근거는 아님 → 6절에서 철회 |

### 5.2 Virtualize

- **케이스 A:** DOM **46행 → 18행** (61%↓)
- **케이스 B:** **30행 → 19행**
- **10~17행** 소형 테이블은 차이 미미 · scrollMs는 현재 규모에선 OFF가 더 낮게 측정

> **정정 (2026-08-01):** 당시 저는 이 DOM 행 수 감소를 "대용량 테이블에서 효과 명확"이라고 적었습니다. 틀렸습니다. 46행 규모에서는 초기 렌더도 스크롤도 개선되지 않고, 스크롤 프레임은 오히려 나빠집니다. 합성 데이터로 46행부터 5만 행까지 다시 측정한 결과는 6절에 있습니다.

### 5.3 Prefetch

- 4케이스 평균 nav: **472ms → 323ms** (prefetch ON + virtualize ON)
- 케이스 B 최대 개선 **623ms → 148ms** · 케이스별 편차 있음

### 5.4 무엇을 유지할 것인가

1. **Virtualize ON 유지** — 행 수가 많은 Task Results에서 DOM을 절반 이하로 줄여 줍니다(케이스 A 46→18행). 소형 테이블(10~17행)에선 이득이 작지만 손해도 없으니 켜 둡니다.
   - **정정 (2026-08-01):** "손해도 없으니"는 사실이 아니었습니다. 100행 이하 구간에서 가상화는 스크롤 FPS를 119 → 75~96으로 떨어뜨리고 long task를 만듭니다. 유지 판단 자체는 그대로 두지만(페이지 크기가 커지는 순간 손익이 뒤집히므로), 근거는 "손해 없음"이 아니라 "**초기 렌더를 사고 스크롤 프레임을 파는 트레이드오프**"입니다. → 6절
2. **Prefetch 유지** — hover prefetch + SSR hydration으로 진입 체감(navMs) 평균을 약 32% 낮췄습니다(472→323ms, 케이스 B 623→148ms).

### 5.5 이 측정의 한계

- **Prefetch가 항상 이기지는 않습니다.** 상세 표를 보면 warm 캐시로 추정되는 케이스에서 OFF가 더 빠른 반례가 있습니다 — 케이스 D는 OFF+OFF **249ms** < ON **369ms**, 케이스 A는 OFF+ON **224ms**가 오히려 최저였습니다. 평균은 개선을 보여 주지만 케이스별 편차(캐시 상태·네트워크 흔들림)가 큽니다.
- **샘플이 케이스당 5회**라 이상치에 민감합니다. median으로 완화했지만 표본이 작습니다.
- **측정 절차상 prefetch ON은 hover를 1초 기다린 뒤 클릭**하므로, "hover할 새도 없이 바로 누르는" 빠른 클릭 시나리오의 이득은 이 수치에 잡히지 않습니다. 실제 이득의 상한에 가깝게 봐야 합니다.

### 5.6 다음에 볼 것

- 캐시 cold/warm을 명시적으로 분리한 재측정, 케이스당 샘플 수 상향(예: 15회).
- 행 수가 훨씬 큰 테이블(수백 행)에서 virtualize의 scrollMs 이득이 역전되는 지점 확인.

## 6. 다시 쟀다 (2026-08-01) — "46행 → 18행"은 근거가 아니었다

> **측정 일자:** 2026-08-01 · **환경:** Storybook + 합성 데이터 · **도구:** Playwright + CDP
>
> **왜 다시 재는가:** 위 5절의 `46행 → 18행(61%↓)`을 두고 이런 지적을 받았습니다. **"겨우 46행 렌더링하던 걸 가상화했다고요? 이거 최적화 맞아요?"**
>
> 맞는 지적입니다. 46행은 가상화 없이도 브라우저가 여유롭게 그립니다. `46 → 18`은 *가상화가 동작한다*는 증거일 뿐 *성능이 개선됐다*는 증거가 아닙니다. 애초에 46이라는 숫자는 Task Results의 `PAGE_SIZE = 100` 안에서 그 페이지에 데이터가 46건 있었다는 뜻일 뿐입니다.

### 6-1. 왜 실서비스 측정으로는 답이 안 나왔나

앞 절들의 측정은 QA API에 실제로 들어 있는 데이터에 묶여 있습니다. 한 페이지가 최대 100행이니 **행 수를 원하는 만큼 올릴 수 없고**, 가상화의 손익분기점이 100행 위에 있는지 아래에 있는지 확인할 방법이 없었습니다.

그래서 이번에는 **합성 데이터**로 갔습니다. `Table` 컴포넌트만 Storybook 스토리에 띄우고, 행 수와 **행당 payload 크기**를 인자로 받아 Playwright가 조합을 순회합니다. API도 인증도 필요 없으니 5만 행까지 자유롭게 올릴 수 있습니다.

측정 설계에서 신경 쓴 부분:

- **타이밍을 페이지 밖에서 잰다** — 드라이버가 `table-perf:start`를 던지면 그때 Table이 마운트되고, 페인트 후 `table-perf:painted`가 돌아옵니다. Storybook 부팅 시간이 측정에 섞이지 않습니다.
- **측정 코드가 먼저 죽지 않게** — 5만 행 비가상화는 DOM이 140만 노드입니다. `querySelectorAll('*')`로 스크롤 컨테이너를 찾으면 측정 코드가 먼저 터지므로, `Table`의 `scrollAreasRef`로 컨테이너를 직접 받고 노드 수는 `getElementsByTagName('*').length`로 셉니다.
- **브라우저가 죽어도 스윕은 계속** — 실제로 첫 실행에서 5만 행 비가상화가 렌더러 프로세스를 죽였고, 복구 로직이 없어 이후 16개 시나리오가 전부 날아갔습니다. 브라우저 풀에 재기동을 넣어 다시 돌렸습니다.
- **스크롤은 px이 아니라 비율로** — 고정 px 스텝은 데이터셋마다 비교가 불가능합니다(6-4에서 상세). 스크롤 가능 범위를 30등분해 어떤 크기든 매 스텝이 실제 이동이 되게 했습니다.

환경: 뷰포트 1600×900, 스크롤 뷰포트 600px, `rowHeight` 52px(표시 가능 약 11행), 9컬럼 중 3개가 장문 텍스트 셀. 스크롤은 전체 범위를 30등분해 프로그램 스크롤하며 프레임과 long task를 셌습니다.

- **그런데 스크롤은 여전히 가상화가 집니다.** 같은 조건에서 비가상화는 119fps · 최악 프레임 9ms를 유지하는데, 가상화는 107fps(46행) · 75.8fps(100행)로 떨어지고 최악 프레임은 4배 이상 나빠집니다. 이미 다 그려둔 DOM을 브라우저가 스크롤하는 게, 매 프레임 보일 행을 계산해 마운트/언마운트하는 것보다 빠릅니다.
- **long task는 이 구간에서 양쪽 모두 0건입니다.** 초기 측정에서 가상화 쪽에 1~4건이 잡혔지만, 그건 아래 6-4에서 설명하는 측정 버그의 부산물이었습니다.
- **힙과 DOM 노드는 이 구간에서 논점이 아닙니다.** 46행 47KB에서 힙 차이는 32.9 vs 35.7MB, DOM은 808 vs 1,479로 둘 다 무해합니다.

### 6-4. 측정 자체가 틀렸던 부분 — 고정 px 스크롤

첫 실행의 스크롤 수치는 **믿을 수 없었습니다.** 저는 뷰포트 단위(600px)로 30번 스크롤했는데, 46행은 콘텐츠가 2,392px이고 뷰포트가 600px이라 실제로 스크롤할 수 있는 거리가 **1,792px뿐**입니다. 즉 3번째 스텝에서 이미 바닥에 닿고, 남은 27번의 `scrollTop` 대입은 아무 일도 하지 않습니다. 그 27번의 **idle 프레임이 FPS 평균을 vsync 상한(약 120fps)으로 끌어올렸습니다.**

반대로 5,000행은 콘텐츠가 260,000px인데 30 × 600px = 18,000px, 즉 **전체의 7%만 긁고** 끝났습니다. 작은 데이터셋은 idle로 부풀고 큰 데이터셋은 앞부분만 재는, **서로 비교할 수 없는 측정**이었습니다.

고친 방법은 단순합니다 — 스텝을 `(scrollHeight - clientHeight) / 30`으로 계산해 **어떤 데이터셋이든 전체 범위를 30등분해 끝까지** 훑게 했습니다. 위 표는 모두 수정 후 수치입니다.

이 버그는 제가 아니라 **교차검증 하네스의 검증자(Codex)가 잡았습니다.** 작성자인 저는 "스크롤을 30회 돌렸다"는 사실에 만족했고, `scrollTop`이 clamp된다는 걸 계산해보지 않았습니다. 작성자와 검증자를 분리해 둔 이유가 이런 데서 드러납니다.

수정으로 결론도 바뀌었습니다. 이전에는 "1,000행부터 가상화가 유효"라고 썼지만, 실제로는 **초기 렌더는 1,000행부터, 스크롤은 5,000행부터**로 손익분기점이 갈립니다. 그리고 "가상화가 long task를 만든다"는 주장은 폐기했습니다 — 편향이 걷히자 가상화 쪽 long task는 전 구간 0건이고, 30~60건은 비가상화 5,000행 이상에서만 나옵니다.

### 6-5. 그래서 무엇이 틀렸고 무엇을 고쳤나

**철회합니다.** `46행 → 18행(61%↓)`을 성능 개선 근거로 쓴 것은 틀렸습니다. 그 숫자는 DOM 행 수가 줄었다는 사실일 뿐이고, 그 구간에서 실제 성능은 **개선되지 않거나 스크롤은 나빠집니다.** 이력서와 경력기술서에서도 이 문장을 뺐습니다.

**대신 이렇게 말할 수 있습니다.**

- **초기 렌더 손익분기점은 약 1,000행**입니다(677 → 90ms, 7.5배).
- **스크롤 손익분기점은 약 5,000행**입니다(15.6 → 63.4fps, long task 30 → 0건).
- 우리 서비스는 `PAGE_SIZE = 100`이라 **평소에는 두 지점 모두에 도달하지 않습니다.** 즉 현재 설정에서 가상화는 "명백한 승리"가 아니라 **초기 렌더를 사고 스크롤 프레임을 파는 트레이드오프**입니다.
- 다만 행이 무거울 때(행당 47KB) 100행 초기 렌더 2.8배는 실재하는 이득이고, 페이지네이션이 없어지거나 페이지 크기가 커지는 순간 손익이 급격히 가상화 쪽으로 기울어집니다.

**남은 판단.** 지금 코드에서 가상화를 끄지는 않았습니다. 끄면 스크롤 프레임은 좋아지지만, 페이지 크기가 커지는 변경 하나로 다시 되돌려야 하고 그 시점은 예고 없이 옵니다. 대신 `overscan`을 줄여 가상화 쪽 프레임 손해를 줄이는 게 다음 실험 후보입니다 — 최악 프레임 25~42ms가 overscan 재계산에서 오는지부터 확인해야 합니다.

### 6-6. 이 측정의 한계

- **합성 데이터입니다.** 셀 렌더러가 단순 텍스트라, 실제 Task Results의 커스텀 셀(배지·툴팁·중첩 테이블)이 갖는 컴포넌트 비용은 빠져 있습니다. 실제 비용은 이보다 큽니다.
- **시나리오당 1회 로드**입니다(`TV_SAMPLES=1`). 페인트 93.5 vs 94.0ms 같은 작은 차이는 노이즈로 봐야 합니다. 7.5배·29배·140배처럼 자릿수가 다른 차이만 결론에 썼습니다.
- **스크롤이 프로그램 스크롤**입니다. `scrollTop`을 뷰포트 단위로 점프시키므로 관성 스크롤이나 트랙패드 연속 입력과는 다릅니다.
- **헤드리스 Chromium 단일 환경**입니다. 저사양 기기나 다른 브라우저 엔진의 손익분기점은 다를 수 있습니다.

재현: `pnpm perf:table-virtual` (`TV_SAMPLES`, `TV_ONLY=rows|payload`로 조정)

### 6-7. 그래서 언제 켜나

두 축의 측정을 합치면 판단표가 나옵니다. 전부 6-2·6-3 표에서 읽은 값입니다.

| 조건 | 초기 렌더 | 스크롤 | 판단 |
| --- | --- | --- | --- |
| 46행 · 행당 10KB 미만 | 차이 노이즈 수준 (93.5 vs 94.0ms) | 가상화가 **짐** (112.9 vs 118.6fps, 최악 프레임 2.6배) | **끄는 게 낫다** |
| 100행 · 행당 10KB 미만 | 가상화 **1.7배 이득** (143.8 → 84.3ms) | 가상화가 짐 (111.8 vs 121.4fps) | 트레이드오프 |
| 100행 · 행당 40KB 이상 | 가상화 **2.8배 이득** (454.6 → 163.2ms) | 가상화가 짐 (75.8 vs 118.5fps) | 초기 렌더를 사고 스크롤을 판다 |
| 1,000행 | 가상화 **7.5배 이득** (677 → 90ms) | 가상화가 **아직 짐** (67.3 vs 81.1fps) | 트레이드오프 |
| 5,000행 이상 | 가상화 **29배 이득** (2,904 → 100ms) | 가상화 **압승** (63.4 vs 15.6fps, long task 30 → 0) | **끌 이유가 없다** |

읽어야 할 지점은 **두 손익분기점이 다르다**는 것입니다. 초기 렌더는 1,000행에서 이미 가상화가 7.5배 이기는데, 스크롤은 5,000행이 되어야 뒤집힙니다. 그 사이 구간에서는 어느 쪽이 사용자에게 더 중요한지 화면 성격이 결정합니다 — 한 번 보고 나가는 화면이면 초기 렌더가, 오래 스크롤하며 훑는 화면이면 프레임이 중요합니다.

행이 무거운 경우(행당 40KB 이상)는 100행에서도 초기 렌더 2.8배가 실재하지만, 같은 조건에서 스크롤은 집니다. "행이 무겁다"만으로 가상화를 정당화할 수 없다는 뜻입니다.

그리고 첫 줄이 처음에 제가 있던 자리입니다. 46행에 행당 400자. 이 구간에서 가상화는 **아무것도 개선하지 않고 스크롤만 나쁘게 만듭니다.**

## 7. 마치며 — 개선을 증명하는 숫자와 동작을 증명하는 숫자는 다르다

이 글에서 제가 틀린 지점을 한 문장으로 줄이면 이렇습니다. **DOM 행 수가 줄었다는 사실을, 성능이 좋아졌다는 근거로 썼습니다.**

둘은 다른 종류의 숫자입니다.

| | 동작을 증명하는 숫자 | 개선을 증명하는 숫자 |
| --- | --- | --- |
| 예 | `domRows` 46 → 18 | 페인트 2,941 → 108ms, FPS 15.5 → 85 |
| 무엇을 말하나 | 내가 켠 기능이 켜졌다 | 사용자 경험이 나아졌다 |
| 언제 필요한가 | 구현 검증, 디버깅 | 성과 보고, 도입 판단 |
| 없으면 | 기능이 도는지 모름 | **효과가 있는지 모름** |

앞의 숫자는 구하기 쉽습니다. DOM을 세면 나오고, 켜고 끄면 바로 갈립니다. 뒤의 숫자는 어렵습니다. 조건을 통제해야 하고, 노이즈를 걸러야 하고, 손익분기점이 어디인지도 같이 찾아야 합니다.

그래서 쉬운 쪽 숫자가 어려운 쪽 자리에 앉기 쉽습니다. `61%↓`는 그럴듯하게 생겼고, 표에 넣으면 다른 성능 수치들과 구분이 안 갑니다. 저도 두 달 동안 구분하지 못했습니다.

**지적 하나가 없었으면 그대로 남았을 겁니다.** 그게 이 일에서 제일 신경 쓰이는 부분입니다. 측정을 안 한 게 아니라 측정을 했는데도 틀렸고, 스스로는 못 잡았습니다. 6절의 재측정도 제가 의심해서 시작한 게 아니라 남이 물어봐서 시작했습니다.

그래서 다음부터 성능 수치를 적을 때 한 줄을 더 쓰기로 했습니다. **"이 숫자가 나빠지면 사용자가 무엇을 느끼는가."** `domRows` 46이 18로 줄어도 사용자는 아무것도 못 느낍니다. 페인트 2.9초가 0.1초가 되면 느낍니다. 이 질문에 답이 안 나오는 숫자는 구현 검증용이지 성과가 아닙니다.

가상화는 지금도 켜져 있습니다. 우리 페이지 크기에서는 명백한 승리가 아니라 초기 렌더를 사고 스크롤을 파는 거래인데, 페이지네이션이 걷히는 순간 손익이 급격히 기웁니다. 그 시점은 예고 없이 옵니다. 다음 실험은 `overscan`을 줄여 가상화 쪽 프레임 손해를 깎을 수 있는지 보는 것입니다.
